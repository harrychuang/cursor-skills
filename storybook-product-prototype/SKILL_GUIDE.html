Storybook Product Prototype

把一個「產品點子」用 PRD 主導的流程,逐步變成「可點擊的 Storybook 原型 + 一整套可交接文件」。產出的不是靜態截圖,而是有路由狀態、轉場觸發、確定性假資料的互動原型。

PRD-led React + TypeScript Storybook Project-agnostic 22 files · SKILL.md + references + scripts + templates
這份說明由實際研讀 skill 內容產生,涵蓋 SKILL.md、5 份 references/、2 支 scripts/、agents/openai.yaml 與全部 assets/prototype-template/ 模板。

這是什麼

這是一個工作流程型(workflow)skill——它不是一個函式庫,而是教 AI agent「怎麼把產品想法拆解成文件、流程模型、假資料,最後組成 Storybook 互動原型」的一套標準作業流程與模板。

核心理念:文件先行、流程先於 UI、資料確定且本地化。文件本身就是耐久的交接物——另一個 agent 不需要任何對話脈絡,只看資料夾裡的文件就能接手。

會幫你做到

  • 從產品點子產出 PRD / UI Flow / Data Spec / Acceptance
  • typed 的路由與轉場 metadata(*Flow.ts)
  • 確定性、本地的假資料(*Data.ts)
  • 可點擊的 React 原型 + Storybook story
  • 把完整流程掛到 parameters.prototype 當審查契約

刻意不做

  • 不呼叫真實產品 API(全部 mock)
  • 不重建像素級截圖,而是做可互動流程
  • 不保證目標專案已有 UI Flow viewer——只負責產出 metadata 契約
  • 不在未經同意下偷偷加 Storybook 相依套件

什麼時候用

情境是否適用
要把一個產品想法變成 PRD + 可點擊原型✅ 主要用途
要 scaffold 一個全新的原型資料夾✅
要驗證原型的文件與 metadata 是否一致✅
純粹要做一個正式上線的 production 功能⚠️ 這是原型工具,不是 production 流程
專案不是 React / 沒有 Storybook⚠️ 需自行調整產出檔(skill 是 project-agnostic 但預期 React/TS Storybook)

前提條件

需要一個 React + TypeScript 的 Storybook 專案當目標。 這個 skill 集合所在的 repo(~/.cursor/skills)本身不是 Storybook app,所以要在你真正的產品專案裡使用它。
  • React / TypeScript 專案,或能改寫產出檔以適配的專案
  • Storybook(模板預設使用 @storybook/react-vite;story 用 ?raw import markdown,需 Vite 環境)
  • Python 3(若要用 scaffold_prototype.py / validate_prototype.py)
  • (可選)專案若已有 prototype inspector / UI Flow viewer,skill 會自動對齊它的 parameters 命名與 preview-mode query 慣例

六步工作流程

skill 內部遵循固定順序:文件 → 流程 → 資料 → UI → 驗證。每一步都不能跳過依賴關係。

1

Frame The Product(界定產品)

寫任何實作檔之前,先確認:產品名與 owner、主要用戶與問題、進入路由與初始狀態、需要的路由與分支狀態、使用者觸發的轉場、要重用的既有元件、每個路由需要的假資料、非目標與必須維持 mock 的外部系統、Storybook 審查的驗收標準。

原則:只問會改變「路由模型、資料契約、驗收標準」的問題,一次問一題。

2

Generate Docs First(先寫文件)

在組 UI 之前,先建立六份文件(見 六份文件)。這些文件是耐久交接物,必須具體到別的 agent 不需私下脈絡就能接手。

3

Model UI Flow Before UI(先建流程模型)

先寫 <feature>Flow.ts 再寫 React 畫面。用穩定 route id(不是顯示文字)、把每個可達畫面加進 route metadata、用 flow-only 節點表達 decision/success/error/loading/async 分支、每個會改變路由的動作都加進 transitions。

4

Create Deterministic Data(建立確定性資料)

寫 <feature>Data.ts:資料全部本地且確定,盡量用既有元件 prop 型別,涵蓋 branch / empty / loading / error 狀態,在 DATA_SPEC.md 記錄 fixture 歸屬與未來 API 替換點。絕不從原型呼叫真實 API。

5

Compose The Storybook Prototype(組原型)

建立 React 原型、CSS、meta、story、index。優先重用既有 design-system 元件;路由狀態以 route id 顯式 typed;點擊透過 route mapping 與 transition trigger 串接(不靠 rendered text);prototype-only CSS 收斂在 feature 根 class 底下;把完整 meta 掛到 parameters.prototype。

6

Validate(驗證)

跑 validate_prototype.py、專案 typecheck(通常 npm run typecheck)、Storybook render/build。除非文件、flow metadata、fixture、story metadata、互動行為描述的是同一個產品行為,否則不算完成。

腳本指令

兩支腳本不一定要手動跑——agent 套用 skill 時會在對應步驟自動呼叫。手動使用方式如下。

scaffold_prototype.py — 從模板拉骨架

python3 scripts/scaffold_prototype.py "Portfolio Alerts" \
  --target-root src/pages/prototypes \
  --owner "Product Team" \
  --entry-route portfolio-alerts

會在 <target-root>/<feature-kebab>-prototype/ 產生整個資料夾(例:portfolio-alerts-prototype/)。

參數說明預設
feature_name人類可讀功能名(必填位置參數)—
--target-root原型根目錄src/pages/prototypes
--titlestory 標題<Feature> Prototype
--ownerowner 標籤Product Team
--entry-route初始 route idfeature kebab 名
--kebab / --pascal / --camel覆寫各種命名由 feature name 推導
--css-class覆寫根 CSS class<prefix>-<kebab>-prototype
--css-prefixCSS class 前綴cm
--force覆寫已存在的模板檔off

命名推導:kebab portfolio-alerts · PascalCase PortfolioAlertsPrototype · camelCase portfolioAlertsPrototype · title Portfolio Alerts Prototype。

validate_prototype.py — 驗證資料夾契約

python3 scripts/validate_prototype.py src/pages/prototypes/portfolio-alerts-prototype

通過印出 Prototype validation passed.;失敗會列出缺漏項並回傳非零 exit code。檢查內容見 驗證與品質門檻。

資料夾契約

每個原型住在自己的資料夾。若專案用 src/screens、app、packages/ui 或不同 story 慣例,根路徑可調整。

src/pages/prototypes/<feature>-prototype/
  <Feature>Prototype.tsx          # React 原型畫面
  <Feature>Prototype.stories.tsx  # Storybook story(掛 parameters.prototype)
  <feature>PrototypeData.ts        # 確定性假資料
  <feature>PrototypeFlow.ts        # typed 路由/節點/轉場 metadata
  <feature>PrototypeMeta.ts        # 匯入 docs + 組出 parameters.prototype
  <feature>-prototype.css          # scoped 在 feature 根 class 下的樣式
  index.ts                          # re-export 元件與型別
  docs/
    PRD.md  FLOW_SPEC.md  UI_SPEC.md
    DATA_SPEC.md  ACCEPTANCE.md  IMPLEMENTATION_GUIDE.md

實作順序(Implementation Order)

  1. 草擬 PRD.md
  2. 草擬 FLOW_SPEC.md
  3. 建立 typed *Flow.ts
  4. 建立確定性 *Data.ts
  5. 組 <Feature>Prototype.tsx
  6. 加 scoped 原型 CSS
  7. 建 *Meta.ts(匯入 docs、輸出 parameters.prototype 資料)
  8. 建 *.stories.tsx
  9. 驗證文件、UI Flow metadata、互動行為、typecheck

六份文件

文件責任必備標題(被 validator 檢查)
PRD.md產品問題、用戶、目標、非目標、旅程、AI 實作範圍、相依Product Summary · Problem · Users · Goals · Non-Goals · Core Journeys
FLOW_SPEC.mdroute id、flow-only 節點、轉場、trigger、狀態規則、導覽對應Source Of Truth · Route Map · Transitions
UI_SPEC.md外殼佈局、組成、視覺狀態、互動規則、RWD、無障礙、design-system 限制Design Principle · Interaction · Accessibility
DATA_SPEC.md確定性 fixture、欄位意義、資料不變量、API 替換點Source Of Truth · Fixture Inventory · API Replacement Points
ACCEPTANCE.md可測試的完成標準:Storybook、metadata、互動、視覺一致性、無障礙、可實作性Storybook · Interaction · Engineering
IMPLEMENTATION_GUIDE.md實作順序、要建立的檔、限制、驗證指令Implementation Order · Required Verification
PRD 寫作規則:寫可觀察的產品行為而非只列實作任務;當審查者可能誤以為有真 API/auth/持久化時,務必寫進 Non-Goals;Core Journeys 要具體到能對應成 route transition。

UI Flow 契約

流程的「真實來源」是 typed 的 *Flow.ts;FLOW_SPEC.md 是同一份契約給人看的版本。三種核心型別:

Route — 產品畫面

type Route = {
  id: RouteId;        // 穩定 route id(React state + 流程圖共用)
  title: string;       // 審查標籤
  navigationId: string;
  component?: string;   // 主要元件 / 組合畫面
  description?: string; // 這個 route 證明的行為
  flowGroup?: string;
  flowPosition?: { x: number; y: number }; // 穩定座標(可選)
};

FlowNode — 非畫面的分支邏輯

用於 API 成功/失敗、async/queued、權限決策、驗證結果、背景狀態等「不是完整產品畫面」的分支。

type FlowNode = {
  id: FlowNodeId;
  title: string;
  description?: string;
  shape: "decision" | "state";
  tone?: "default" | "success" | "error" | "warning";
  flowPosition?: { x: number; y: number };
};

Transition — 使用者觸發的路由變更

type Transition = {
  from: FlowTargetId;   // 來源 route 或 flow-node id
  to: FlowTargetId;     // 目標 route 或 flow-node id
  trigger: string;       // 穩定事件名,如 submitButton.click
  label: string;         // 邊線的人類可讀標籤
  kind?: "primary" | "return" | "global" | "secondary" | "outcome" | "condition";
  flowLine?: "key" | "reference" | "hidden"; // key = 畫在簡化畫布上
};
畫布 vs 索引:UI Flow 簡化畫布只畫 flowLine: "key" 的轉場;完整轉場清單仍保留在 metadata(Transition Index 用)。

驗收條件

  • 每個可見 route 都出現在 route metadata
  • 每個有記錄的點擊都出現在 transition metadata
  • 每個 transition 的 target 都存在(是 route 或 flow-only node)

Trigger 命名

用穩定、面向實作的名稱當作路由邏輯——不要用畫面上顯示的文字當邏輯。

動作類 
quoteRow.click
submitButton.click
topAction.search
settingsSheet.dismiss
bottomNavigation.watchlist
結果/分支類 
orderSubmit.success
orderSubmit.error

先建立 mapping 物件(bottom nav id → route id、top action id → route id、tab/menu/sheet action id → route id)再串 handler。

Data 契約

Fixture 規則

  • fixture 本地且確定;盡量用既有元件 prop 型別
  • 以 route 或 domain 命名 fixture 群組
  • 流程含 branch 節點時要有對應 branch fixture
  • 狀態在範圍內時要有 empty / loading / disabled / error fixture
  • 絕不從原型呼叫真實產品 API

DATA_SPEC.md 區段

Source Of Truth · Fixture Inventory · Route Data Requirements · Data Schemas · API Replacement Points · State And Branch Fixtures · AI Update Rules

API 替換點(每個未來 API/服務都記錄)

endpoint/服務名 · method · request shape · response shape · owning team/來源 · 哪些 route 消費它 · 目前用哪個 fixture 群組 mock。

資料不變量(UI 與測試依賴的)

  • 當 route key 用的穩定 id
  • 每張卡/列的必填欄位
  • 控制視覺狀態的 direction / status 值
  • 觸發 success / error 流程的 branch fixture 值

Storybook 整合

Story 需求

  • 渲染完整產品畫面時用 layout: "fullscreen"
  • 渲染可點擊原型(非靜態截圖)
  • 把 meta 物件掛到 parameters.prototype
  • 若目標專案的 UI Flow viewer 用 iframe,支援 route preview 模式(模板用 ?prototypeFlowPreview=true query 偵測)
const meta = {
  title: "Pages/Prototypes/<Title>",
  component: FeaturePrototype,
  tags: ["autodocs"],
  parameters: {
    layout: "fullscreen",
    prototype: featurePrototypeMeta,   // ← 審查契約
  },
} satisfies Meta<typeof FeaturePrototype>;

Meta 物件形狀

欄位:id · title · description · owner · status · docs · flow · data。

docs 以 ?raw 匯入六份 markdown;flow 暴露 routes / nodes / transitions;data 摘要 fixture 清單、route 資料需求、API 替換點、來源歸屬。

UI Flow Viewer 邊界:這個 skill 只產出 metadata 契約,不保證目標 Storybook 已有 prototype inspector。若沒有:仍產出 parameters.prototype、在文件說明 Docs/Data/UI Flow 的審查需要某個 addon 或專案自備 viewer、未經要求不要默默加相依套件。若已有 inspector,則對齊它的 parameter 名與 preview-mode query 慣例。

驗證與品質門檻

validate_prototype.py 會檢查

檔案存在

  • *Prototype.tsx(component)
  • *Prototype.stories.tsx(story)
  • *PrototypeFlow.ts(flow)
  • *PrototypeData.ts(data)
  • *PrototypeMeta.ts(meta)
  • *-prototype.css(css)
  • index.ts
  • docs/ 六份 + 必備標題

內容契約

  • story 含 parameters、prototype:、fullscreen layout
  • meta 含六份 docs 的 raw import、flow:、data:、docs:
  • flow 含 RouteIds、Routes、Transitions,且至少一個穩定 route id 字串

還要跑(依目標 repo)

  • 專案 typecheck — 通常 npm run typecheck
  • Storybook render / build — 通常 npm run storybook 或 npm run storybook:build
  • 若專案有 prototype inspector,手動審查 Story / Docs / Data / UI Flow

品質門檻(Quality Bar)

  • 原型是可點擊的產品流程,不是靜態截圖重建
  • PRD / UI Spec / Flow Spec / Data Spec / Acceptance / Storybook metadata 彼此一致
  • UI Flow 由 route + flow-node + transition metadata 生成
  • fixture 確定且本地
  • parameters.prototype 是審查契約
除非文件、flow metadata、fixture、story metadata、互動行為描述的是同一個產品行為,否則不標記為完成。
