Componentization Workflow

Figma Componentize

找出設計稿中還不是元件的 UI，在 Components 頁面由小到大建立元件、variants 與元件屬性， 透過 figma-m3-variables 的 Workflow F 建立並套用 tokens，最後把原稿換成 instance，並逐一證明外觀沒有改變。 無法證明一致的原稿一律保留。

偵測 → 分組 → 建立 → Tokens → 替換 原稿比對通過才刪除 Tier 0–3 Workflow F

前置條件

開始前先確認三項前置條件。

前置條件 如何確認
可寫入的 use_figma 工具工具清單中有 use_figma；只有 get_screenshot 這類唯讀的 Figma 工具不夠
figma-use skill可以讀取。第一次呼叫 use_figma 前先讀，每次呼叫都傳入 skillNames: "figma-componentize"
含 Workflow F 的 figma-m3-variablesSKILL.md 有「F. Tokenize hardcoded values」，且 references/value-harvest.md 存在

缺少任何一項就停止，說明缺少什麼，不做任何寫入。

use_figma 的限制：

  • 每次呼叫都從第一頁開始，也不能一次載入所有頁面，所以要用 setCurrentPageAsync 逐頁作業。
  • 只能使用 async getter。
  • 每次呼叫最多回傳 20 kB，並有執行時間上限；失敗的呼叫可能留下部分變更。
  • 無法儲存版本，也尚不支援自訂字型與新增圖片。

提問時使用編輯器的提問工具（Cursor 為 AskQuestion、Claude Code 為 AskUserQuestion）；沒有提問工具時，以文字詢問並等待回覆。

何時使用

範圍由設計師決定：丟一個 section 就處理裡面的 UI，丟單一元件的連結就處理那個元件。不要求同一個 UI 重複出現，一個按鈕也能做成 Button 元件。範圍或分組不明確時，先詢問。

需求 使用
把 section、frame 或單一元素中的散圖層做成元件，並把原稿換成 instance本 skill
只把寫死的數值轉成 tokens，不建立元件figma-m3-variables Workflow F
套用現有 tokens、稽核 tokens，或建立 token 系統figma-m3-variables（Workflow A–E）
從零建立完整的 design systemfigma-generate-library

不在範圍內

  • team library 的元件：只沿用本檔案的 local components
  • 把散落的向量圖示整理成圖示庫：只列在報告中
  • prototype 互動與元件動畫
  • 重新排版，例如把絕對定位改成 auto layout：元件保留原稿的圖層結構
  • 在 Components 頁面產生說明文件 frame
  • Code Connect 與程式碼端元件

通用規則

適用於每一個步驟。

  1. 先檢查再寫入每個步驟都先以唯讀的呼叫確認目前狀態。
  2. 一次一個呼叫use_figma 不可平行執行；每個腳本都依 ID 重新取得節點，而且一次只處理一頁。
  3. 回傳精簡偵測結果以 OFFSET 分頁，直到 nextOffset 為 null；建立時一次一個元件或一個 component set；替換一次最多 50 個；每次回傳都控制在 18,000 字元內。
  4. 替換前不動原稿原稿只有在對應的 instance 通過驗證後才刪除。
  5. 詢問，不猜測每個 needs-review 的分組都要詢問。與現有元件的配對結果只要不是 exact，也要詢問，不自行決定是否沿用。近似值不自動合併，由使用者在 Workflow F 的比對板上決定。
  6. ID 對照表從第一次寫入起維護 ID 對照表（還原點、頁面、元件、實例），每次呼叫後更新。
  7. 錯誤處理發生錯誤時停止並閱讀錯誤訊息，再依 ID 對照表重新讀取受影響的節點，只重試未完成的部分，不盲目重跑。

變動分級

沿用 figma-m3-variables 的 Tier 0–3 定義：0 是唯讀；1 是單一明確目標、外觀不變；2 是批次或結構性、外觀不變；3 會改變外觀或具破壞性。

步驟 級別 確認方式
掃描、偵測、分組、計畫、報告Tier 0不需確認
分組比對區塊（暫時的 Section，只新增）—決定前允許建立，決定後刪除
Components 頁面、主元件、variants、元件屬性Tier 2計畫確認；使用者明說不需審閱即可略過
在現有的 component set 新增 variantTier 2只有設計師為該分組選了「在現有元件加一個 variant」才執行；即使之前說過「全部自動套用」也不能略過
Tokens依 Workflow FWorkflow F 的 token 計畫；合併近似值是 Tier 3
解除鎖定（只在使用者同意時）Tier 2明確確認
把原稿換成 instanceTier 3一定要確認，並附上基準截圖與元件連結；即使之前說過「全部自動套用」也不能略過
接受保留實例列出的差異Tier 3先顯示差異，再逐一確認

步驟總覽

十個步驟依序進行；每個步驟的細節在後面各節與參考文件中。

10

從範圍到報告

觸發：設計師分享 section、frame 或元素的連結，並要求元件化、建立元件或把散圖層換成 instance

  1. 範圍與基準（Tier 0）：接受節點連結或目前的選取範圍，找出每個範圍所在的頁面。超過 50 個頂層 frame 或跨頁時，先確認範圍。為每個範圍截圖作為基準。
  2. 偵測（Tier 0）：先逐頁執行偵測腳本取得分組，再依偵測到的骨架與名稱，收集相關的現有元件清單。清單不是空的，才帶著清單再偵測一次，確定每個實例要沿用哪個現有的 variant；清單是空的，第一次偵測的結果就是最終結果。最後取得每組的實例清單。
  3. 分組比對：在範圍旁建立 Componentize Review — temporary 區塊，逐組詢問接受、改名、拆分、合併或排除。與現有元件有關的分組另外詢問：是否沿用、沒有合適 variant 的實例怎麼處理，以及與現有元件同名時的新名稱。決定後刪除區塊。
  4. 計畫：列出元件、沿用的現有元件、要新增的 variants、不沿用而新建的元件、設計師決定保留的實例、排除、近似值差異、問題與各 Tier 的寫入摘要，等待確認。
  5. 還原點：請使用者手動存一個版本「Before figma-componentize — {範圍名稱}」，確認後才開始寫入，並開始維護 ID 對照表。
  6. 建立（Tier 2）：找出或建立 Components 頁面，依 atom → molecule → organism 建立元件、合併並排列 variants、加上元件屬性。設計師選了「在現有元件加一個 variant」的分組，在這一步把 variant 加進現有的 component set；沿用的分組不建立元件。
  7. Tokens：以新元件與新增的 variants 為範圍呼叫 Workflow F；計畫中的近似值差異加入它的比對板。
  8. 替換（Tier 3）：確認後只替換最外層的實例，每次最多 50 個，逐項驗證。
  9. 驗證：為每個範圍截圖並與基準比對，回報非預期的差異；清除追蹤標記與暫時區塊。
  10. 報告：元件、沿用的現有元件與新增的 variants、tokens、已替換與保留的實例、還原點、Components 頁面連結，以及 ID 對照表。

偵測規則

偵測完全唯讀，逐頁執行，結果精簡並分頁回傳。

候選條件（任一成立即可）

  • 符合 UI 模式：依圖層名稱（中英文皆可）判斷；按鈕與卡片也可以依結構判斷
  • 結構簽章在範圍內出現兩次以上，且有自己的樣式或至少兩個子節點
  • 設計師直接指向的單一元素本身

層級

  • atom：不含其他候選，最先建立
  • molecule：含 atom
  • organism：含 molecule，最後建立
排除 規則
既有元件與 instanceCOMPONENT、COMPONENT_SET、INSTANCE 與其中的所有內容
畫面層級 frame直接位於 page 或 section 下（或不是單一元素的範圍本身），寬 320–1920 px、高至少 480 px
純排版外框沒有自己的填色、描邊、效果或圓角，且至少一個直接子節點是候選（名稱符合模式者優先成為候選）
隱藏圖層visible === false，連同其子節點
鎖定圖層連同其子節點；ID 列入報告。鎖定不會擋住外掛寫入，但代表設計師的意圖
單獨的文字與形狀不在任何候選內的文字與形狀

分組規則

以結構簽章分組，而不是以截圖的相似度分組，所以每一組都能說明為什麼分在一起，也能推導出元件屬性。

描述 內容 用途
核心簽章依子節點順序排列的結構角色與 auto layout 方向（遞迴）；不含圖示與巢狀 instance核心簽章相同的候選成為同一個元件
排版簽章核心簽章，加上無 auto layout 時子節點的位置與 constraints，以及固定尺寸文字框的大小instance 無法覆寫這些屬性；不同時提議為 needs-review 的 variants
樣式填色、描邊、陰影、圓角、padding、間距、高度，以及第一段文字的顏色與字級Style、Size、State variants，或近似值差異
內容文字、圖示與 instance 的位置（leading、trailing）、圖片填色元件屬性
實例之間的差異 結果
只有文字不同同一個元件，TEXT 屬性
巢狀圖示 instance 不同同一個元件，INSTANCE_SWAP 屬性
部分實例多一個 leading icon同一個元件，BOOLEAN 屬性
圖片不同同一個元件，以 instance 覆寫圖片
填色、描邊或陰影的類型不同，結構相同Style variants（Filled、Outlined、Text、Tonal、Elevated）
高度差異超過近似門檻Size variants（Small／Large 等）
透明度降低，或名稱含狀態字詞State variants（Enabled、Disabled、Hovered、Pressed、Focused、Selected）
子節點結構不同不同的元件
數值在近似門檻內（例如 padding 15 與 16）同一個 variant；差異列出並交給 Workflow F 的比對板
子節點位置、constraints 或固定文字框尺寸不同提議為 Style variants（例如 Filled、Filled 2），標為 needs-review
同類別、狀態與尺寸，但顏色、間距或排版差異超過門檻第二種樣式（例如 Filled 2），標為 needs-review
非 instance 的向量圖示不同needs-review：先把圖示做成元件

近似門檻與 Workflow F 相同：顏色 CIE76 ΔE ≤ 3 且 paint 透明度相同；數值差 ≤ 1 px，或 ≤ 較大值的 5%（取較大者）。

  • 畫面被排除，並排兩個按鈕的外框是純排版外框，也被排除
  • 三個按鈕是 atom，卡片是 molecule
  • Button 是 component set：Style=Filled、Style=Outlined，以及 TEXT 屬性 Label
  • 15 px 的按鈕留在 Style=Filled，padding 差異交給 Workflow F 的比對板
信心度 條件
exact至少一半的成員依名稱符合模式，且排版簽章一致
inferred只依結構或重複出現判斷

分組與本檔案現有元件的比對方式、配對結果，以及設計師可以選擇的做法，見沿用現有元件。

沿用現有元件

本檔案已經有合適的元件時，優先沿用，不另外建立；沒有合適的元件，或設計師決定不沿用時，才建立新元件。每個分組都會和現有元件比對三件事：骨架、名稱、外觀。

骨架

  • 圖層種類、順序與 auto layout 方向，也就是分組規則中的核心簽章
  • 骨架相同是必要條件：原稿的文字與圖示依圖層位置帶進 instance，骨架不同就無法證明外觀不變
  • 骨架相同的現有元件全部列為候選

名稱

  • 名稱或 UI 類型與分組相同的現有元件優先
  • 名稱明顯是不同類型的（按鈕對上 Chip），不會自動沿用
  • 圖層沒有命名、只靠結構推測出類型的分組，不算有名稱證據

外觀

  • 顏色、描邊、陰影、圓角、padding、間距、高度與字級
  • 每個實例各自比對：現有元件有 variant 落在近似門檻內，才算有外觀相近的 variant
  • 相近的 variant 不只一個時，取差異最少的那一個

三種配對結果

結果 什麼情況 會發生什麼
exact骨架相同、名稱相符，而且每個實例都有外觀相近的 variant直接沿用，不另外詢問
partial骨架相同、名稱相符，但有些實例沒有外觀相近的 variant有相近 variant 的實例照樣沿用；沒有的由設計師決定
unconfirmed骨架與外觀都相符，但名稱無法確認是同一種 UI提議沿用，並詢問設計師：「沿用 {名稱}」、「不沿用，建立新的」、「改沿用另一個元件」或「維持原樣」
不自動沿用名稱是不同類型；或名稱無法確認，而且有實例的外觀不相近不沿用。這些元件列為「骨架相同的其他元件」，設計師可以改選其中一個
由設計師選擇兩個現有元件的配對程度相同不自行挑選，詢問要沿用哪一個

每個實例在偵測階段就確定要用哪個 variant，替換時直接使用，不會到替換時才發現沒有 variant 可用。這裡的 exact 是配對結果，和分組信心度的 exact 是兩件事。

沒有合適的 variant 時

配對結果是 partial 時，沒有相近 variant 的實例依 variant 分開詢問，例如 Outlined 的那幾個問一次。有相近 variant 的實例不受影響，仍會換成現有元件的 instance。設計師決定之前，這個分組不建立、不新增，也不替換任何東西。

選項 結果
「在現有元件加一個 variant」在現有的 component set 裡新增一個 variant，這些實例換成它的 instance。只有現有元件是 component set 時才提供
「建立新元件」這些實例另成一組，建立新的元件；名稱由設計師確認，不能與現有元件同名
「維持原樣」不替換，原稿保持原樣；列入計畫與報告，原因是「沒有相符的 variant，設計師決定保留」

現有元件是單一元件（不是 component set）時，只提供「建立新元件」與「維持原樣」，並說明原因：單一元件不能加 variant。想加的話，可以先在 Figma 把它合併成 component set，再重新執行。

範例

檔案裡有 Chip，以及只有 Style=Filled 的 Button component set。畫面上有兩個填色按鈕和一個外框按鈕，圖層名稱都是「Button」。這一組配對到 Button，配對結果是 partial。

對象 結果 原因
現有元件 Button配對到這個元件骨架相同，圖層名稱「Button」與元件名稱相符
現有元件 Chip不自動沿用骨架相同，但名稱是不同類型；列為「骨架相同的其他元件」
兩個填色按鈕沿用外觀與 Button 的 Style=Filled 相近，之後換成它的 instance
一個外框按鈕詢問設計師Button 沒有外觀相近的 variant，提供三個選項：「在現有元件加一個 variant」、「建立新元件」、「維持原樣」

在現有 component set 加 variant 的做法與保護

這會改到設計師原有的 component set，屬於 Tier 2 的變動，而且只在設計師為該分組選了「在現有元件加一個 variant」時才執行；之前說過「全部自動套用」也不算同意。

項目 做法
來源從原稿的 clone 建立，原稿本身不動
名稱使用這個 set 自己的屬性名稱，不強制改成 Style、Size、State。例如屬性是 Type 與 Size 的 set，新 variant 命名為 Type=Secondary, Size=md。名稱由設計師確認
圖層名稱與屬性連結比照最接近的現有 variant，所以 set 原有的元件屬性在新 variant 上同樣有效
位置放在現有 variants 下方 20 px
現有內容現有的 variant 不移動、不改名、不改樣式、不刪除；set 不新增任何屬性
寫入後的檢查新 variant 在 set 裡、variant 剛好多一個、每個現有 variant 的位置與尺寸都沒變、沒有多出屬性
檢查不通過移除新 variant、把 set 還原，再請設計師選「建立新元件」或「維持原樣」
旁邊的圖層set 變大後如果蓋到旁邊的圖層，只回報，不移動任何東西

「不沿用，建立新的」

  • 分組比對時，有配對到現有元件的分組可以選
  • 這一組不沿用現有元件，改為建立新元件
  • 計畫與報告會記錄沒有沿用哪一個元件

「改沿用另一個元件」

  • 從列出的「骨架相同的其他元件」中選一個，或提供本檔案中某個元件的連結或名稱
  • 設計師指定的元件不需要名稱相符，外觀仍會逐一比對
  • 指定元件的圖層結構不同時，會說明無法證明外觀不變，不沿用它，改問「建立新元件」或「維持原樣」

同名時先問名稱

  • 不會建立與本檔案現有元件同名的新元件
  • 先請設計師提供可以區分的名稱（例如 Outlined Button），或排除這個分組
  • 改名、拆分或決定建立新元件之後，都會再檢查一次名稱

限制：

  • 只比對本檔案的元件；team library 的元件不比對。
  • 圖層結構略有不同的現有元件（例如多包一層 frame）仍然認不出來，不會沿用。但如果它與分組同名，名稱檢查會先詢問，不會默默建立一個重複的元件。

分組比對區塊

在 Figma 裡直接看到每一組的實際樣子，再決定分組、命名與拆併。有配對到現有元件的分組，現有元件會並排顯示在原稿樣本旁邊。數值的近似值差異則用 Workflow F 的 Token Review — temporary 比對板。

放在哪裡

  • 範圍所在頁面、既有內容右側 400 px 的 Section
  • 名稱固定為 Componentize Review — temporary
  • 只新增這個 Section，不移動、不修改既有節點

每組內容

  • 標題：名稱 · 信心度 · component、set 或 reuse（直接沿用）
  • 對應：variants 與元件屬性
  • 實例數量與備註
  • 最多四個代表實例的 clone，縮放到 400 px 寬內
  • 原稿樣本旁並排現有元件的樣本：配對到的元件最多兩個 variants，「骨架相同的其他元件」最多三個
  • 每個現有元件的樣本標示元件名稱與 variant 名稱；配對到的元件另標配對結果，「骨架相同的其他元件」另標名稱比對的結果
  • 現有元件的樣本是 instance，會隨區塊一起刪除；區塊不會在檔案中新增任何元件

決定與收尾

  • 截圖並提供 Figma 連結
  • 逐組選擇：接受、改名、拆分、合併或排除；每個 needs-review 都要問
  • 有現有元件的分組多兩個選項：「不沿用，建立新的」與「改沿用另一個元件」
  • 另外會問：是否「沿用 {名稱}」、沒有合適 variant 的實例怎麼處理、兩個元件配對程度相同時沿用哪一個，以及同名時的新名稱
  • 需要時重新偵測，最後刪除 Section

建立元件

建立是 Tier 2：只新增頁面、Section 與元件，以及設計師選擇加進現有 component set 的 variant；原稿在替換之前完全不動。

還原點

  • use_figma 無法存版本
  • 寫入前請使用者按 ⌘⌥S（Windows 為 Ctrl+Alt+S）或選 File → Save to version history
  • 名稱為「Before figma-componentize — {範圍名稱}」，確認後才寫入

Components 頁面

  • 優先使用名稱含 components 或「元件」的頁面
  • 沒有就建立 Components
  • Starter 方案每個檔案最多 3 頁：改在使用者指定的頁面建立 Components Section

由小到大

  • atom → molecule → organism
  • 每次呼叫只建立一個元件或一個 set
  • 較大元件中的較小元件換成 exposed instance

從 clone 建立主元件

  • 先載入代表實例用到的所有字型，再 clone 到元件的 Section 中
  • clone 中自動命名的子圖層改用結構名稱（label、leading-icon、container、headline、supporting-text）
  • 轉成元件後檢查回傳節點的類型與子節點數量；轉換失敗時先包進 frame 再轉換，並記錄下來

元件屬性

  • 合併成 set 後才加在 set 上，並連到每個 variant
  • TEXT、BOOLEAN、INSTANCE_SWAP
  • 圖示差異一律用 INSTANCE_SWAP，不做成 variants

在現有 component set 加 variant

  • 只在設計師為該分組選了「在現有元件加一個 variant」時執行，每次呼叫只加一個
  • 從原稿的 clone 建立，名稱使用該 set 自己的屬性，放在現有 variants 下方 20 px
  • 現有的 variant 不移動、不改名、不改樣式、不刪除，set 也不新增屬性
  • 寫入後檢查不通過，就移除新 variant、把 set 還原，再詢問「建立新元件」或「維持原樣」

沿用的分組

  • 不建立元件
  • 實例之後直接換成偵測時確定的現有 variant
  • 細節見沿用現有元件

Variants 的格狀排列

合併後的 variants 會疊在同一個位置，所以要依 Figma 官方慣例排列：State 的值為欄，其餘屬性的組合為列，間距 20 px、內距 40 px，預設 variant 在左上角，最後依內容調整 set 的尺寸。一個 set 最多 30 種組合，超過就依某個屬性拆成多個 set。

State=Enabled State=Disabled Style=Filled Label Label Style=Outlined Label Label

虛線框為預設 variant（Style=Filled, State=Enabled）。

項目 規則 範例
元件或 setTitle Case，取自 UI 模式或有意義的圖層名稱；重名時加上描述字或編號；不與本檔案的現有元件同名Button、List Item、Product Card
Variant屬性=值，順序為 Style、Size、State，只列有多個值的屬性；加進現有 set 的 variant 使用該 set 自己的屬性Style=Outlined, State=Disabled
元件屬性依結構命名Label、Headline、Show leading icon、Leading icon
Section與元件或 set 同名，每個元件一個，不與既有內容重疊Button

Tokens 與 Workflow F

建立完成後、替換之前，以新元件為範圍呼叫 figma-m3-variables 的 Workflow F，讓之後替換上去的 instance 直接繼承綁定。加進現有 component set 的 variant 也在範圍內。

{ "scope": ["40:9", "42:7"], "components": ["Button", "Card"], "caller": "figma-componentize" }

傳入

  • scope：新主元件、component set，以及加進現有 set 的 variant 的 ID（不含原稿）
  • components：計畫中的元件名稱
  • caller：figma-componentize

回傳

  • variables：Ref、Sys、Comp 的 variable ID
  • styles：Text 與 Effect Style 的 ID
  • bindings、mergedGroups、skipped

規則

  • Workflow F 的分級、比對板與 token 計畫確認不變
  • 回傳內容全部寫進報告

近似值差異：計畫中只出現在原稿上的數值（例如某個按鈕的 padding 15）會以額外候選值加入 Workflow F 的比對板，樣本是那些實例，放在元件的數值旁邊，但不為它們建立 tokens 或綁定。使用者合併的值（mergedGroups）在替換驗證時視為預期變化；沒有合併的差異會讓該實例保留原稿。

使用者拒絕 token 計畫或 Workflow F 失敗時，先詢問是否在沒有 tokens 的情況下繼續替換；確認後才繼續，報告中標示這些元件未 token 化。

替換原稿

替換是 Tier 3：一定要確認，而且只在 instance 通過驗證後才刪除原稿。

確認時附上

  • 每個元件與 variant 的實例數量、由外層 instance 一併處理的數量，以及已知會保留的實例與原因
  • 偵測時截的基準圖
  • Components 頁面上每個元件 Section 的連結
  • 還原點名稱，以及「每個原稿都要等 instance 通過驗證才刪除」的說明

選項：全部替換 · 選擇元件 · 先不要。選「先不要」時直接產生報告：元件保留，原稿不動。

最外層優先：只替換最外層的實例。卡片裡的按鈕不另外替換，因為卡片的主元件已經含有 exposed 的 Button instance，原本按鈕的文字會複製到這個巢狀 instance 上。外層實例被保留時，它裡面的實例才另外替換。

每個實例的處理順序

記錄原稿狀態 → 隱藏原稿 → 在同一個 parent 與 index 插入 instance → layoutPositioning → 位置（relativeTransform） → resize() → sizing → 複製內容 → 比對
  • 記錄 parent、index、relativeTransform、尺寸、constraints、layoutPositioning、sizing、layoutGrow、layoutAlign、GRID 位置、可見性、名稱與絕對座標。
  • 先隱藏原稿，新 instance 才不會在 auto layout 中推擠兄弟節點。
  • resize() 會把 sizing 重設為 FIXED，所以 sizing 最後設定。HUG 只用在 instance 有 auto layout 時，FILL 只用在 auto layout 的子節點。
  • 手動排列的 GRID 用 setGridChildPosition；自動流向（ROW_AUTO_FLOW）的 GRID 由圖層順序決定位置。

內容如何複製到 instance

原稿與 instance 的結構簽章相同，所以依結構位置對應：文字與圖片依順序，圖示依位置（例如 leading icon#0），巢狀實例對應到相同位置的 exposed instance。

原稿 instance 得到
文字連結的 TEXT 屬性；沒有屬性時直接覆寫
少了選用的圖示連結的 BOOLEAN 屬性設為 false；沒有屬性時直接隱藏
不同的巢狀 instance（例如圖示）連結的 INSTANCE_SWAP 屬性；沒有屬性時用 swapComponent，再遞迴複製它的內容
圖片填色沿用原稿的 imageHash（use_figma 不能新增圖片）
巢狀實例（卡片裡的按鈕）exposed instance 先切換到正確的 variant，再透過它自己的屬性複製內容
圖層名稱有意義的名稱保留（例如「Submit button」）；自動名稱（Frame 12、Group 5）改用元件名稱

setProperties 用錯 key 時不會報錯，所以每個屬性、切換與圖片覆寫都會讀回確認；讀回不一致就視為比對失敗。

逐項驗證

刪除任何東西之前，先把 instance 和記錄的原稿狀態比對。一致才刪除原稿；不一致就刪掉 instance、恢復原稿的可見性，原稿完全不變並列入報告。

檢查 一致的條件
位置與尺寸absoluteBoundingBox 的 x、y、寬、高相差都在 0.5 px 內
文字可見文字的內容與順序完全相同
可見圖層會繪製內容的可見圖層數量相同：文字、形狀、向量、圖片，以及有自己的填色、描邊、效果、透明度或 auto layout 的 frame；純排版外框不算
樣式每個圖層的填色與描邊（以 Workflow F 的正規化形式比對：8 位元 hex 加 paint 透明度）、圖層透明度、描邊寬度、圓角、效果、字型、字級、padding、間距
讀回每個屬性、切換與圖片覆寫都讀回為設定的值

可以解釋的差異：

  • 樣式差異：只有在 Workflow F 的近似門檻內，且使用者已在 Workflow F 合併該值時，才視為一致。
  • 尺寸差異：同一個實例有這類已核准的合併，且差異在 1 px 或 5% 內時，才視為一致。
  • 文字、圖層數量與讀回的差異：一律不能解釋。

使用者看過差異後，可以接受個別實例的樣式與尺寸差異並重新替換（Tier 3）。

比對結果 處理
位置、文字、圖層都相同刪除原稿
位置相差 0.3 px刪除原稿（在 0.5 px 內）
寬度相差 2 px刪除 instance、保留原稿並回報（width 120 → 122）
文字「Send」變成「Save」刪除 instance、保留原稿並回報
padding 因已核准的合併改變（15 → 16）刪除原稿，變化列為已核准
填色不同且沒有合併刪除 instance、保留原稿並回報

原因 何時 接著怎麼做

安全機制

每一層都保留回頭的路：原稿直到驗證通過才刪除，失敗的呼叫可以追蹤與復原。

還原點

第一次寫入前，請使用者手動存一個命名版本，確認後才繼續。

ID 對照表

記錄原稿 → 元件 → instance，每次呼叫後更新，失敗時用來判斷哪些已完成。

逐項驗證

每個 instance 都和原稿比對；不一致就刪掉 instance、恢復原稿。

追蹤標記與復原

每個新 instance 以 shared plugin data 標記原稿 ID。呼叫中斷時，先清掉未完成的 instance、恢復原稿，再只重試未完成的部分。

最終截圖比對

替換完成後為每個範圍截圖，與基準比對；非預期的差異回報，不默默修正。

收尾

清除追蹤標記，刪除仍存在的暫時比對區塊。

報告

最後的報告讓設計師知道建立了什麼、換了什麼、保留了什麼，以及如何回到原本的狀態。

與其他 Skill 的分工

元件化（偵測、分組、建立、替換）與 tokens（數值、語意、綁定）是兩種不同的判斷，分別由兩個 skill 負責。

Skill 職責
figma-usePlugin API 基礎，必須優先讀取
figma-componentize偵測散圖層、分組、在 Components 頁面建立元件、把原稿換成 instance 並驗證（本 skill）
figma-m3-variablesTokens：本 skill 的 token 步驟呼叫它的 Workflow F；另外也負責套用、稽核與建立 token 系統
figma-generate-library完整 design system 建置；本 skill 的 variants 格狀排列與命名沿用它的慣例
