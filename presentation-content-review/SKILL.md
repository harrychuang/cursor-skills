# Presentation Review｜簡報內容審查

協助設計師檢查一份簡報稿是否「每頁標題都是一個結論（觀點＋行動）、副標用理由補充、每頁有 1–3 個證據支撐結論」，並給出可以直接照改的建議。

預設交付**審查報告**，不是改好的簡報。使用者明確要求時，才輸出整份改寫稿或依規則起草。

## 規則來源

- 規則全部在 [references/rules.md](references/rules.md)。**每次審查開始前先完整讀取這個檔案**，以它為準；本文件不重複規則細節。
- 規則有版本號與固定 ID（T 標題、S 副標、E 證據、D 整體）。報告開頭寫出使用的規則版本。
- 判定拿不準時讀 [references/examples.md](references/examples.md) 校準。示例不是規則，與 rules.md 不一致時以 rules.md 為準。
- 使用者提出新規則、修改或停用規則時，依下方「規則迭代」處理。

## 輸入

- 接受 Markdown、純文字大綱、貼上的逐頁文字。每頁至少要能分出標題；副標與內文可缺，缺了就照規則判定為缺少。
- 簡報檔（pptx、key、pdf）、圖片或連結：用目前環境可用且已授權的能力擷取文字。無法讀取時直接說明，請使用者貼文字或提供 Markdown 匯出，不猜內容。
- 分頁不明確時（例如一整段沒有分頁標記的文字），先寫出自己假設的切法，再依切法審查。
- 只有純封面（只有題目、講者、日期）、目錄、章節分隔頁、附錄標為「不適用」。看起來像開場頁但內文有成果、數據或判斷的頁一律照審。
- 沒有任何簡報內容、只有規則討論時，回應規則問題或執行規則迭代，不憑空審查。

## 審查流程

1. **拆頁。** 列出每頁的標題、副標、內文重點。原文有頁碼就沿用，沒有就依順序編號。
2. **逐頁套規則。** 對每頁依 rules.md 判定標題（T）、副標（S）、證據（E）各項。判定只用「通過／需修改／缺少」，每項附原文引用或轉述作為依據。
3. **逐一檢查證據。** 先數這頁有幾個獨立證據（同一產品的同一次成果只算一個）。每個證據檢查四要素：主體、做法、成果、來源；判定它是否**直接支持這頁的結論**而不只是跟主題有關；標示強度：已驗證成效／做法參考／預期待驗證。缺的要素逐項列出。
4. **整體檢查。** 把所有主體頁的標題依序串成一段話讀一遍，看故事線是否成立、結論是否互相矛盾、同一證據是否被拿去支持不同結論。
5. **產出報告。** 依 [references/review-report-template.md](references/review-report-template.md) 的結構輸出：總評、標題故事線、逐頁表與證據清單、必改清單（依優先順序）、改寫建議、待補證據清單、本次未檢查的項目與限制。使用者只要重點時用精簡版。

嚴重度依 rules.md 定義：**必改**（標題缺觀點或缺行動、零證據、證據與結論無關、疑似捏造、結論互相矛盾）、**建議**（副標沒給理由、證據缺成果或來源、超過 3 個證據、故事線有缺口）、**可選**（用字調整）。有任何必改項目時，總評不能寫「可送出」。

## 改寫建議的原則

- 標題、副標可以直接改寫成建議版本。標題寫成一句結論：觀點＋行動；副標寫理由，接在標題後面加「因為」要讀得通。
- **證據不捏造。** 原文沒有的數字、產品、成果、來源，一律寫成「【待補：需要什麼】」，說清楚要補哪個主體、做法、成果或來源。不填造百分比，不虛構案例。
- 原文的證據若只證明「有人這樣做」，改寫時標為做法參考，並另列一項待補的成效證據。
- 他人回報的成果寫成「該團隊回報」，不改寫成我們必然得到的結果。
- 超過 3 個證據時，指出最直接支持結論的 1–3 個保留，其餘建議移到附錄或拆頁；不是直接刪掉。

使用者要求**補找證據**時，用目前可用且已授權的查詢能力，讀取原文後才引用，附實際來源；查不到就在待補清單說明缺口，不宣稱已查證。查找方法與案例寫法可沿用 `executive-proposal` 的作法，但不必為此另跑一次完整起草流程。

## 三種模式

- **審查（預設）**：輸出報告。
- **整份改寫**：使用者說「直接改成符合規則的版本」時，每頁輸出改寫後的標題、副標、證據行，缺的證據保留【待補】，文末附待補證據清單。先給報告再改寫；使用者只要改寫稿時可省略逐頁表，但必改項目與待補清單不省略。
- **依規則起草**：使用者只給主題或資料、要求新寫一份時，可先用 `executive-proposal` 起草，再用本 skill 的規則審一遍後交付；同一份內容的流程只跑一次，不重複詢問相同資料。

## 規則迭代

這套規則會持續變動。使用者提出新規則、修改既有規則或說某條不要時：

1. 只改 [references/rules.md](references/rules.md)：新規則用該組下一個空號並標「使用者規則」；修改就改條文；停用就在該條與「已停用規則」區標日期與原因，不刪除、不重新編號。
2. 更新版本號與檔尾的版本紀錄（新增功能或規則升次版號，條文修正升末位）。
3. 用一兩句話向使用者複述新規則的判定方式與嚴重度，請他確認；之後的審查立即套用。
4. 流程沒變就不改本文件；只有輸入、步驟或報告結構改變時才更新 SKILL.md 與模板。

使用者若在審查中順口說「以後標題都要⋯⋯」，視為新增規則，照上面處理並在當次報告套用。

## 交付前自檢

- 每一頁都有 T1、S1、E1 與證據品質的判定，而且每個判定都附得出原文依據？
- 證據數算法一致：同一成果沒有重複計算，計畫與流程說明沒有被當成證據？
- 改寫建議裡有沒有任何原文沒有的數字、案例或來源？有就改成【待補】。
- 必改清單有依優先順序排列，且總評與必改清單一致？
- 報告開頭有規則版本；無法讀取、未查證、不在範圍的事項都列在末尾？

## 不做的事

- 不審查版面、配色、字型與圖表樣式；不評估講者表達。
- 不產生 PowerPoint、Google Slides 或 PDF；使用者要檔案時，先交付內容，再依環境可用能力處理，並如實說明產生了什麼。
- 不代替使用者決定簡報立場；審查的是「結論有沒有說清楚、有沒有證據」，不是結論對不對。
