一套流程，
讓每個 App 都摺得好。

從盤點、設計決策、實作到自動化截圖驗證。Lego 與非 Lego 的 iOS App 都能用。

流程

五個階段，每一步都有產出。

先讓畫面開合後會重新排版，再談版面。每個決定都記下來、拍成截圖給設計師看。

  1. 盤點

    掃出寫死螢幕尺寸的程式碼，修掉或列例外。

    工程docs/duo/inventory.md

    設計師回答 10 題，決定這個 App 的版面。

    設計師docs/duo/decisions.md

問卷

設計師只要回答 10 題。

每題的預設都是照系統。只有截圖看得出問題，才往下改。

  1. Q1系統直欄用
  2. Q2按鈕怎麼進直欄有直欄就進
  3. Q3直欄上下怎麼分系統預設
  4. Q4按鈕要不要各自一顆系統預設
  5. Q5標題列留什麼系統預設
  6. Q6直欄與視窗底色系統預設
  7. Q7哪些頁改清單＋內容兩欄全部單欄
  8. Q8底線頁籤在橫向維持橫排
  9. Q9開放哪些方向直向＋landscapeLeft
  10. Q10Tab 列系統 Tab

為什麼用問卷，不給標準答案

幾個 App 各自做了 Duo 適配，選擇都不一樣，歸納起來是三種做法：

做法按鈕適合
照系統標準按鈕，分組和位置交給系統改動最少、不會踩到系統限制；先從這裡開始
合起才進直欄內螢幕留在標題列，外螢幕才進直欄希望內螢幕維持原本的標題列
上導覽下動作全部進直欄：返回在上、動作在下按鈕多、標題長，想讓內容區最乾淨

答案寫進 templates/duo-decisions.md，沒決定的題目一律用預設，不猜。每個做法的理由和代價見設計決策。

設計決策

每個做法，都說得出為什麼。

預設照系統。以下是截圖看出問題時可以選的做法，每項都附理由、代價和依據。

✕ 不建議的樣子✓ 建議做法依據：HIG 指南・問卷題號・規則編號

按鈕怎麼分組

同一顆膠囊等於告訴使用者「這幾個是一組」。分組看功能，不看位置。

返回鍵自成一顆

為什麼
返回是導覽，意思是離開這頁；旁邊的分享是動作，意思是對這頁做事。包在同一顆裡，使用者會以為它們是同一類，也比較容易按錯。
代價
只在有直欄時這樣做。水平標題列的分組一改，一般 iPhone 也會跟著變，為此冒回歸風險不划算。

HIG V3・Q4・L7

同類動作放同一組

為什麼
分享和收藏都是對這則內容做的事，性質相近、常一起用，放同一組就看得出它們是一夥的。分組交給系統，間距會自動一致；不要自己加空白去隔開。
代價
幾乎沒有，這就是系統預設。要注意「同類」看的是功能，不是原本是不是排在隔壁。

HIG V6・Q4・L9

性質差很多的動作分開

為什麼
「設定提醒」會建立一個之後持續通知的設定，「分享」按完就結束。後果不同的按鈕放在同一組，使用者會用同樣輕的心情去按；分開之後，一眼看得出哪一顆比較重。
代價
只在大螢幕套用，一般 iPhone 不動。拆太多顆會讓直欄變長、提早溢位，所以只拆真的不同的那一顆。

HIG V4、V6・Q4・L8

按鈕放在哪裡

使用者靠位置找按鈕。每個姿態都放在同一個相對位置，就不用重新學。

上導覽，下動作

為什麼
使用者到直欄上方只會找「回去」；動作集中在底部，就只要記一個地方。不論哪個姿態，返回都在上、動作都在下，換姿態不用重新學。
代價
沒有直欄時（內螢幕直向、一般 iPhone）要把按鈕搬回標題列，而且只搬按鈕、不重建頁面。原本放在左上的動作鈕也要一起移到底部。

HIG V2、V3・Q3・L3–L6、L11

有 Tab 列時，動作接在返回下方

為什麼
系統把直欄底部留給 Tab 圖示，工具列項目排不進去。這是系統限制，不是設計偏好。
代價
同一個 App 會有兩種排法：有 Tab 的頁面動作在上方，沒有 Tab 的頁面動作在底部。審閱前先跟設計師說清楚，免得被當成錯誤。

系統實測・Q3・L5

寬按鈕留在標題列

為什麼
直欄只有 84 pt 寬。比它寬的自訂按鈕、或不是標準按鈕的自訂元件，放進直欄會變成一塊白色。
代價
標題列就不是「只留標題」了。想進直欄，要另外設計一個窄版（符號＋標題）。

HIG V8・Q5・L10

直欄的樣子

直欄要看起來像獨立的一欄，顏色固定，而且永遠在同一邊。

標題列背景停在直欄左邊

為什麼
導覽列寬度由系統決定，縮不短。背景如果滿版，會壓住直欄上方的時間和訊號，直欄就不像獨立的一欄。按鈕都進直欄後只留標題，標題也不會被擠。
代價
要用透明背景圖把右段切掉；沒有直欄時要恢復滿版和底線。

HIG V1・Q5・L1、L2

直欄固定一種底色

為什麼
直欄會透出底下頁面的顏色。深色 App 一打開白底網頁，整條直欄就變白、時間變黑字，看起來像換了一個 App。
代價
要在直欄的位置鋪一塊底色，層級夾在頁面內容和導覽列之間。合起時頂端露出白底也是同一個問題，要補視窗底色。

Q6・L12、L29

直欄固定在右邊

為什麼
直欄在哪一側由硬體決定。兩個橫向都開放，轉到另一側時直欄會跑到左邊，所有按鈕跟著換邊。只開 landscapeLeft，直欄就永遠在右側。
代價
往另一側轉時，畫面不會跟著轉。這是取捨，要請設計師確認。

HIG V2・Q9・L15

橫向多出來的寬度

多出來的寬度拿來放內容，不是把同樣的東西拉長。

底線頁籤改到左側

為什麼
橫向又寬又矮，一整排頁籤占掉的高度，就是少掉的內容。改成左側直排後，左側欄和右側直欄對稱，內容區最高。
代價
左側欄要從導覽列下緣開始排，避開螢幕圓角；標題和內容要往右讓出 120 pt。轉回直向時收回橫排，選中的頁籤不變。

HIG V1、H2・Q8・L16–L19

分段切換鈕留在原地

為什麼
「月／季／年」這種膠囊切換，控制的是眼前這張圖表，屬於內容的一部分，不是頁面之間的導覽。搬到側邊，就離開了它控制的東西。
代價
要先分清楚每一排頁籤是哪一種。分錯了，會把內容的控制項搬走。

HIG V7・Q8・L17

清單頁分成兩欄

為什麼
單欄時每一列被拉到 860 pt 寬，每點一項都要返回一次。左清單、右內容就像 iOS 設定 App，大螢幕多看一層。
代價
只在內螢幕橫向；外螢幕和直向維持單欄。右側要先放一個預設內容（空白像壞掉），但它不算使用者點的：不送點選紀錄，收回單欄時直接丟掉。右側不能再包一層導覽控制器。

HIG H2、R2・Q7・L20–L25

不管選哪個做法，這四件事都要做

  • 移除寫死的螢幕尺寸

    啟動時記下的寬高，開合後就錯了，畫面不會重排。

    盤點 r1–r5
  • 開合不改變選取狀態

    分頁、篩選、清單選取都不變；摺起再打開，要回到同一個地方。

    HIG H2・L30
  • 內容只建一份

    換版面只換位置和父容器、不重新載入，畫面才不會閃、捲動位置才不會跑掉。

    HIG H5・L31
  • 每個直欄項目都有標題＋符號

    溢位選單和 VoiceOver 都靠標題；沒有標題，溢位選單是空白、VoiceOver 唸圖檔名。

    HIG V8・L14

試過、後來撤掉的做法

  • 停用直欄

    外螢幕的標題被擠掉，設計審閱沒通過；另一個 App 也是先停用、後來改回來。→ 照系統用直欄。

    Q1
  • 動作鈕留在直欄上方

    使用者到直欄上方只找返回，動作鈕放在那裡反而不好找。→ 移到底部，和其他動作一組。

    L6
  • 兩欄右側再包一層導覽控制器

    系統直欄一次只顯示一條導覽列的按鈕，外層的按鈕整顆消失，還多讓出一次 84 pt。→ 右側直接嵌入內頁。

    L25

做法會隨審閱改變；每次改都要補 Before／After。

這裡挑了最常被問的 12 個決定；完整 33 條規則與實測數值見 references/layout-rules.md，HIG 指南編號見 references/hig-summary.md。

實作

兩條軌道，同一套規則。

所有改動都放在預設關閉、只在大螢幕（短邊 > 440 pt）生效的開關後面。

Lego 生產線 App

打開共用層的開關。

直欄按鈕、左側欄、兩欄、影音內頁都已做進共用框架；App 依問卷答案設定，主 Tab 建立前完成。

// didFinishLaunching，主 Tab 建立前
let isLarge = { isCurrentSceneLargeScreen() }
LegoVerticalBar.isEnabled = true
LegoVerticalBar.placesAllItemsInColumn = true
LegoSegmentSideMenu.isEnabledProvider = isLarge
LegoMoreSplitLayout.isEnabledProvider = isLarge
references/track-lego.md
非 Lego App（UIKit／SwiftUI）

用系統 API 照做。

每條規則都對到 UIKit 的做法，並附實際適配時踩過的坑。

#if compiler(>=6.4)  // iOS 27.1+
item.axisBehavior = .verticalPreferred
item.sharesBackground = false
// 已顯示的按鈕要先清空再指定才會移動
navigationItem.rightBarButtonItems = nil
navigationItem.rightBarButtonItems = items

自動化 QC

模擬器自己摺，自己拍。

工具與 App 無關；分頁名稱、彈窗、要走哪些頁，全部寫在一份 JSON。

  1. 摺疊／展開duo_hinge
  2. 依計畫走訪walk-plan.json
  3. 截圖＋階層shots/、xchg/
  4. 規則判定analyze.py
  5. 報告report.py

走訪計畫長這樣

{
  "app": { "readyElement": {"button": "首頁"},
           "launchDismiss": [{"label": "我明白了"}] },
  "scenarios": [{
    "id": "A", "mode": "matrix",
    "postures": ["folded", "unfolded",
                 "unfolded-portrait", "refolded"],
    "screens": [
      {"id": "01-首頁", "steps": [{"tab": "首頁"}]},
      {"id": "02-內頁", "steps": [{"tab": "首頁"},
                                 {"firstCell": true}],
       "leaveAfter": true }]
  }]
}

導航都在摺疊時做（展開時的點擊會落到外螢幕），之後只切姿態、不碰畫面。

會自動抓到

  • 嚴重content-missing

    開合後內容整個不在畫面上。

  • 嚴重window-size

    視窗沒跟著螢幕變，畫面不會重排。

  • 高cached-screen-size

    元件寬高等於另一塊螢幕：啟動時快取的尺寸。

  • 高restore-mismatch

    摺回後位置與原本不同。

規則判定只是候選；每張截圖都要人看過。

開始

說一句話就能開始。

把 App 路徑和設計師的名字告訴 agent，說清楚這次做到哪個階段。

用 $ios-foldable-adaptation 幫 <App 路徑> 做 iPhone Duo 適配，設計師是 <名字>，這次先做盤點和問卷。
用 $ios-foldable-adaptation 對 <App 路徑> 跑 Duo QC 情境 A 和 L，報告放 <目錄>。
用 $ios-foldable-adaptation：依 docs/duo/decisions.md 的答案改 <頁面>，做完補 Before／After。
環境

Xcode 27.1、iOS 27.1 iPhone Duo 模擬器、Python 3＋numpy。

設計師

回答問卷、審閱每輪的前後對照、決定待決事項。
