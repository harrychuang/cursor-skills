Install the Storybook Tools suite — generic pages under the Storybook sidebar's Tools category. Current tools:

- **Component Coverage Analyzer** — developers submit UI images / PRD text, an AI skill analyzes them against the project's component catalog, and developers review the resulting coverage report (可直接使用 / 需擴充 variant / 缺少需新建) before implementation.
- **Component Timeline** — every catalogued component in creation order, newest first. Dates come from the first git commit of each catalog entry's `componentPath`; each card renders the component's live story so previews never go stale.

## How the installed system works

```
Storybook Tools pages (React UI, template)         ← Component Coverage Analyzer + Component Timeline
  ↕ fetch /__component-coverage/*                  ← dev API (vite plugin, coverage tool only)
outputs/component-coverage/requests/<id>/          ← request.json + uploaded images (NOT committed)
outputs/component-coverage/reports/<id>.json       ← coverage reports (committed, review state included)
outputs/storybook-tools/TEMPLATE_MANIFEST.json     ← installed manifest copy (records installedTools)
src/storybook/componentCatalog.ts                  ← per-project catalog (GENERATED, shared by all tools)
src/storybook/componentTimeline.ts                 ← per-project timeline data (GENERATED by build script)
src/storybook/component-coverage/
  compositionPreviewRegistry.tsx                  ← trusted project-owned real-component fixtures
src/storybook/component-timeline/
  timelineExtrasRegistry.tsx                      ← project-owned extras slot (default: no extras)
.agents/skills/component-coverage-analyze          ← shared project skill for Cursor and Codex
.claude/skills/component-coverage-analyze          ← byte-identical Claude Code mirror
.agents/skills/component-coverage-implement        ← shared implementation skill for Cursor and Codex
.claude/skills/component-coverage-implement        ← byte-identical Claude Code mirror
```

Path contracts, per-tool file lists, skill source-to-target mappings, and expected skill hashes live in `template/TEMPLATE_MANIFEST.json` (`sharedCore` plus a `tools` map — one entry per tool with its own `files`, `installTargets`, `checks`, and `pathContracts`). Runtime paths are mirrored in code (`coverageApi.ts` ↔ `vite-plugin.mjs` ↔ `.storybook/main.ts`). The report/review data contract's single source of truth is `src/storybook/component-coverage/coverageTypes.ts`; the timeline data shape's single source of truth is the generator `scripts/component-timeline/build-component-timeline.mjs`.

## Two responsibilities, strictly separated

1. **Deterministic copy** — template files are copied VERBATIM. Do not rewrite, reformat, or "improve" them. Only the files listed under each tool's *Permitted adaptations* may be modified, and only in the ways listed.
2. **AI binding** — everything project-specific is generated or wired by you: the component catalog, trusted composition preview renderers, the `main.ts` wiring, the accent and preview-surface tokens, the story-entry imports, the generated timeline data, and the verification run.

## Tool selection

- **Default: install every tool** in the manifest's `tools` map.
- When the user names a subset (e.g. "only the component timeline"), copy only the `sharedCore` files plus the named tools' files, and wire only the named tools' checks into the target's `check` chain. The shared core (catalog contract + catalog check) is installed in every case.
- Record the installed tool set as an `installedTools` array when writing the manifest copy (see *Install flow*, last step). Update runs use it to know what to update and what to offer as an addition.

## Preconditions (check before touching anything)

Shared:

- The target is a React Storybook project. Locate the template: the `template/` directory next to this SKILL.md.
- If `outputs/storybook-tools/TEMPLATE_MANIFEST.json` — or the legacy `outputs/component-coverage/TEMPLATE_MANIFEST.json` — already exists in the target, this is an **update**, not a fresh install — jump to *Update mode*.

Per tool (check only for tools being installed; a failed tool-specific precondition blocks THAT tool with an explanation, not the whole install):

- **component-coverage**: the project uses the **Vite builder** (`@storybook/react-vite` framework, or another Vite-based React setup). The dev API is a Vite `configureServer` middleware — it cannot work on the Webpack builder. Also: the target has reusable components with stories. If it has none, warn the user that coverage analysis needs a component library to match against, and ask whether to proceed (the tool will render, but every block would be "missing").
- **component-timeline**: the target repository has **full (non-shallow) git history** — verify with `git rev-parse --is-shallow-repository` (must print `false`). A shallow clone would stamp every component with the clone date; refuse to install the timeline tool and explain this, while continuing with any other requested tools.

## Install flow

### Shared core (always)

1. Copy `scripts/check-component-catalog.mjs` verbatim.
2. **Generate the component catalog** — the core binding step. Read `references/catalog-authoring.md` first, then:

   - Inventory the project's reusable components: story files, component sources, any existing component docs.
   - Write `src/storybook/componentCatalog.ts` starting from `componentCatalog.template.ts` (then delete the `.template.ts` copy from the target — the target keeps only the real catalog). Every entry needs the real `storyTitle` (copied from the story file or its autotitle) and a real, existing `componentPath`.
   - Scope: reusable library components only — not screens/pages/prototype compositions.
   - Present the generated catalog to the user for review before finishing; catalog quality decides analysis quality.

3. Optional alias (ask or follow project convention): `"check:component-catalog": "node scripts/check-component-catalog.mjs"`. When added, hook it into the existing aggregate `check` script.

If the target's stories live somewhere other than `src/` (check `stories:` globs in `.storybook/main.*`), keep the template's internal layout intact and place the whole `src/…` subtree at the equivalent covered location, keeping the relative structure (`storybook/component-coverage` and `storybook/component-timeline` next to `storybook/componentCatalog.ts`, story entries under a `stories/tools/` folder the globs cover).

### Tool: component-coverage (when selected)

1. **Copy the tool's template files verbatim** (paths are target-repo-relative, identical to the template layout):

   - `src/storybook/component-coverage/` — all 10 files
   - `src/stories/tools/ComponentCoverageAnalyzer.stories.tsx`
   - `scripts/component-coverage/vite-plugin.mjs` + `vite-plugin.d.mts`
   - `scripts/check-component-coverage-reports.mjs`, `scripts/check-component-coverage-agent-skills.mjs`, `scripts/check-component-coverage-preview-contract.mjs`
   - `template/skills/component-coverage-analyze/` → each target declared by `installTargets`: shared `.agents/skills/` plus the `.claude/skills/` mirror
   - `template/skills/component-coverage-implement/` → the same shared `.agents/skills/` plus `.claude/skills/` mirror pattern

   Copy each upstream skill source separately to every target declared for it. Do not create per-agent source variants inside this template; the installed checker verifies every destination against the manifest's SHA-256 hash. Cursor and Codex both discover the shared `.agents/skills/` copy, while Claude Code uses `.claude/skills/`; do not add a redundant `.cursor/skills/` copy.

2. **Permitted adaptations** (the ONLY template edits allowed for this tool):

   - `ComponentCoverageAnalyzer.stories.tsx`: change the `@storybook/react-vite` import to whatever module the project's existing stories import `Meta`/`StoryObj` from.
   - `compositionPreviewRegistry.tsx`: add direct imports for target-project components that can render with deterministic, side-effect-free fixture props. Register zero-argument renderers by `ComponentCatalogId`, and optionally map a catalog id to an exact story id through `getCompositionPreviewStoryId` so the preview iframe and Inspector story link target that variant. The registry may evolve into richer entries as long as the `getCompositionPreviewRenderer`/`getCompositionPreviewStoryId` accessor signatures hold. Keep the empty scaffold for components that cannot be rendered safely; the preview will show a documentation fallback. Never read renderer props, imports, children, CSS, or executable content from a report.
   - `component-coverage.css`, `--cca-accent` (marked "Install binding"): point it at the project's primary color token with the current hex as fallback, e.g. `var(--their-primary-token, #e8590c)`. Keep the plain hex if no token system exists.
   - `component-coverage.css`, `--cca-preview-bg` (marked "Install binding"): point it at the target product's normal page/surface background token. Keep `var(--cca-bg)` when the product has no suitable token.
   - `component-coverage.css`, light-theme selector (marked "Install binding"): replace `:root[data-cca-theme="light"]` with the attribute/class the project's Storybook theme switcher actually sets. Leave as-is when there is no switcher (tool stays dark).

3. **Wire `.storybook/main.*`**:

   - Import and register the dev API plugin inside `viteFinal` (create `viteFinal` if absent):
     ```ts
     import { createComponentCoverageApiPlugin } from "../scripts/component-coverage/vite-plugin.mjs";
     // in viteFinal:
     plugins.push(createComponentCoverageApiPlugin());
     ```
   - Add to `staticDirs`: `{ from: "../outputs/component-coverage", to: "/component-coverage" }` (adjust `from` to be correct relative to the `.storybook` dir).

4. **Create the data directory**: `outputs/component-coverage/reports/.gitkeep`, and add a `.gitignore` rule for `outputs/component-coverage/requests/` (requests hold local working images — never committed; reports ARE committed).

5. **Wire validation scripts**:

   - Add the required aliases `"check:coverage-reports": "node scripts/check-component-coverage-reports.mjs"`, `"check:coverage-agent-skills": "node scripts/check-component-coverage-agent-skills.mjs"`, and `"check:coverage-preview": "node scripts/check-component-coverage-preview-contract.mjs"`. Agent handoff prompts call the underlying Node scripts directly, so they remain package-manager-neutral; the aliases keep the checks discoverable to developers and aggregate scripts.
   - Hook all three required aliases into an existing aggregate `check` script.

## Verify (all must pass before reporting success)

Shared:

1. `node scripts/check-component-catalog.mjs` passes.
2. The project's typecheck (or `tsc --noEmit`) passes with the new files.
3. A production build (`storybook build`) succeeds.

component-coverage (when installed):

4. `node scripts/check-component-coverage-reports.mjs` passes.
5. `node scripts/check-component-coverage-agent-skills.mjs` passes, confirming both analyze and implement skills match their manifest SHA-256 hashes across the shared `.agents` copy and Claude Code mirror.
6. `node scripts/check-component-coverage-preview-contract.mjs` passes, confirming the installed preview, selected-block UI Reference evidence crop and fallback, Inspector, selection clearing, report disclosure, and new-window documentation affordances remain intact after adaptation.
7. Storybook dev starts; `GET http://localhost:<port>/__component-coverage/state` returns JSON (`{"requests":[],"reports":[]}` on a fresh install).
8. The `Tools/Component Coverage Analyzer` page renders with the intake form (submit stays disabled until an image or PRD text is provided), and the Storybook index contains no redundant `Review Preview` story.

component-timeline (when installed):

9. `node scripts/check-component-timeline.mjs` passes (regenerates in memory and byte-compares `src/storybook/componentTimeline.ts`).
10. The `Tools/Component Timeline` page renders: components grouped by creation date (newest first), cards showing catalog name/category with live story previews, pager present when more than 30 components exist, and no extras section (default registry).

Report to the user: tools installed, files installed, catalog entry count, timeline entry count (and untracked ids, if any), adaptations made, and how to use each tool (coverage: submit in the tool → copy the analysis prompt to Cursor, Claude Code, or Codex → review in the tool → copy the implementation prompt to the same agent — both handoffs use agent-neutral prompts with a `.agents/skills/` fallback path, and both project skills are mirrored byte-for-byte for Claude Code; timeline: regenerate with the `build:component-timeline` npm script after adding components).

1. Read `outputs/storybook-tools/TEMPLATE_MANIFEST.json` first. ## Guardrails

- Template files are vendored: no edits beyond each tool's *Permitted adaptations*, ever — fixes belong upstream in this skill's `template/`.
- Keep one upstream source per component coverage skill in `template/skills/` and install it to every manifest target. Never maintain separate upstream agent variants.
- Recompute the matching `skillContentSha256` value whenever an upstream skill source changes. Hash UTF-8 text after normalizing CRLF to LF, matching `check-component-coverage-agent-skills.mjs`; the checker treats a stale hash as a failed installation.
- Use `.agents/skills/` as the shared Cursor/Codex location and `.claude/skills/` as the Claude Code mirror. Do not install duplicate `.cursor/skills/` copies.
- Never fabricate catalog entries for components that don't exist, and never let `storyTitle`/`componentPath` drift from reality — the check scripts, the analyze skill, and the timeline generator all depend on them.
- `coverageTypes.ts` is the data contract's single source of truth; the vite plugin, check script, and companion skills mirror it. If you change one, you must change them all — which is another reason not to change any of them during install.
- `src/storybook/componentTimeline.ts` is generated — never hand-edit it; regenerate with the build script. Its check treats any drift from git history as a failure.
- Keep analysis and implementation handoffs agent-neutral; do not add agent-specific slash commands or tool names.
- Keep `compositionPreviewRegistry.tsx` and `timelineExtrasRegistry.tsx` project-owned and deterministic. Reports may select a catalog id but must never supply renderer props, imports, JSX, styles, or executable content; timeline extras must never execute content derived from user input.
- Do not commit anything in the target project unless the user asks; list the created/modified files instead.
