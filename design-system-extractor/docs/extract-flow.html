Design System Extractor Skill

Extract 流程與目的

多語系導覽，說明這個 skill 如何從圖片、Figma URL、專案資料夾 extract evidence、設計原則、tokens、components 與開發者文件。

流程導覽

01 / 05

輸入來源

  • 圖片與 screenshots
  • Figma URL、exports、variables
  • Project 或 prototype folders
  • Vibe-coded prototype 專案

核心約定

先 extract 有 evidence 支撐的設計規範。除非明確要求，product UI code 只會在 checkpoint 之後才開始。

輸出內容

Markdown 規範、設計原則、嚴格 ref -> sys -> comp tokens、 duplicate source review、近似 token 決策、component similarity review、integration review records、anti-AI style rules、HTML docs 與 audit results。

流程判斷點

從來源到 checkpoint 的五個階段

先把來源整理成 evidence，再把 evidence 變成規範；遇到重複來源、 近似 token 或相似 component 時，進入 review queue，而不是直接新增。

01

Evidence first

將圖片、Figma 與程式線索整理成可追溯的設計證據，並先檢查重複來源。

02

Principles

把重複出現的判斷整理成可執行的產品設計原則。

03

Token structure

依照 ref、sys、comp 分層，並把近似數值留給開發者確認。

04

Component review

用 inventory、fingerprint 與預覽證據找出可能重複的元件。

05

Docs and audit

產出 HTML 文件、review queue 與 audit 結果，再進入 checkpoint。

多人協作流程

開發者先送 PR，整合者再集中整併

每個開發者只負責自己的元件 branch；整合者從 main 開 integration branch，逐一 review 和 merge，最後用 integration PR 回到 main。

開發者

  1. 從最新 main 開 ds/new-comp。
  2. 用 skill 萃取自己的 Figma 元件。
  3. 跑 docs、strict audits 和 self-review。
  4. push branch，開 PR 到 main，等待整合者處理。

整合者

  1. 從最新 main 開 ds/integration-round-1。
  2. 逐一 review 開發者 PR 或 branch。
  3. 用 INTEGRATION_REVIEW.md 記錄 merge、blocked 或 request changes。
  4. 重產 docs、跑 strict audits，開 integration PR 回 main。
main → developer branches / PRs → integration branch → integration PR to main

How the extract flow works

The skill turns visual and code references, including vibe-coded prototypes, into a portable design-system package that future agents and developers can trust.

Extract flow

  1. Discover inputs

    Locate screenshots, image exports, Figma links, variables, routes, Storybook stories, CSS, token files, vibe project keep/ignore notes, rendered browser captures, and existing agent rules. Normalize source fingerprints and flag duplicate inputs before they become separate evidence.

  2. Create the evidence map

    Record where each decision comes from: source, observed region, source fingerprint, pattern, affected token or component, and confidence.

  3. Extract design principles

    Turn repeated evidence into 5-7 product principles, each with a clear name, supporting observations, implementation rule, and confidence level.

  4. Extract foundations

    Define product character through color, type, typographic composition, spacing, density, shape, elevation, imagery, data display, and state language.

  5. Build token architecture

    Convert raw values into reference tokens, semantic roles into system tokens, and component slots into component tokens. Order color scales as 100 lightest to 0 darkest, and pause for merge/keep-distinct review when values are very close.

  6. Inventory components

    Identify repeated UI, layout, graphic, and typographic patterns and classify them as extracted, planned, blocked, or out of scope. Compare component fingerprints and add visual review assets when a candidate overlaps an existing component.

  7. Extract component specs

    Write anatomy, variants, states or display modes, accessibility rules, and token slots for high-value reusable components, including text lockups when the evidence supports them.

  8. Define composition and interaction rules

    Capture page rhythm, layout density, typographic lockup placement, navigation patterns, motion expectations, and state behavior.

  9. Add anti-AI style constraints

    Block unsupported generic UI patterns such as inflated spacing, decorative gradients, glass panels, or invented illustration styles.

  10. Generate developer HTML

    Render Markdown specs and token tables into docs/design-system/index.html and render review candidates into docs/design-system/review.html so developers can scan both the system and open review items.

  11. Audit and checkpoint

    Run source, token, and component audits, update session state, list open questions, and stop before implementation work changes the scope.

Design principle extraction

Find repeated choices

Compare screens or nodes and identify decisions that appear consistently: density, emphasis, hierarchy, restraint, contrast, motion, and feedback.

Name the behavior

Write principles as product behavior, not decoration. Example: "dense lists stay readable" is stronger than "use compact UI."

Convert to rules

Each principle must become an implementation rule that can guide tokens, components, layout, state, and future UI work.

Keep uncertainty visible

If evidence is partial, mark the principle as medium or low confidence and record what source would confirm it.

Why these extracts matter

Principles align judgment

They give future agents a decision model when no exact token or component already covers a new interface case.

Evidence prevents guessing

Every rule is traceable to an image, Figma node, route, or source file, and duplicate sources are reviewed before they increase confidence.

Tokens prevent drift

Strict inheritance keeps raw values, semantic roles, and component decisions separate and easier to audit. Near-token review prevents accidental duplicates.

Inventory prevents duplication

Components are reused or extended intentionally instead of being recreated with slightly different anatomy.

HTML improves handoff

The generated documentation gives developers a readable index of rules, tokens, and component specs.

Output contract

Source of truth

design-system/*.md and tokens/*.css remain the editable source files.

Reading layer

docs/design-system/index.html is generated from the source files for developer review, and docs/design-system/review.html summarizes near duplicate sources, near tokens, and similar components.

Agent handoff

Claude Code, Cursor, and Codex should read the same specs, token rules, anti-AI constraints, and session checkpoint.

Quality gate

Source audits, token audits, near-token decisions, and session-state updates make the extraction repeatable across projects.

抽出フローの考え方

この skill は、画像、Figma、プロジェクトフォルダを根拠として、 将来の AI エージェントと開発者が同じ判断で使える デザインシステム一式に整理します。

抽出フロー

  1. 入力を確認する

    スクリーンショット、画像書き出し、Figma URL、Variables、 画面ルート、Storybook、CSS、token、rendered browser captures、 既存の agent ルールを確認し、source fingerprint で重複入力を先に見つけます。

  2. 根拠マップを作る

    判断の出典、観察した領域、パターン、影響する token または component、source fingerprint、確信度を記録します。

  3. デザイン原則を抽出する

    繰り返し見える根拠を 5-7 個の product principles に変換し、 名前、観察事実、実装ルール、確信度をセットで記録します。

  4. 基礎要素を抽出する

    色、文字、文字組み、余白、密度、角丸、奥行き、画像、 データ表示、state 表現からプロダクトらしさを定義します。

  5. token 構造を作る

    生の値は reference token、意味を持つ役割は system token、 component の slot は component token に分けます。色階は 100 を最も明るく、0 を最も暗くし、近い値は merge または keep-distinct の確認を取ります。

  6. component を棚卸しする

    繰り返し使われる UI、layout、graphic、typographic パターンを見つけ、extracted、planned、blocked、 out-of-scope に分類します。近い component は fingerprint と visual review asset で比較します。

  7. component spec を抽出する

    重要な再利用 component について、構造、variant、state または表示 mode、アクセシビリティ、token slot を文書化します。 evidence があれば text lockup も対象にします。

  8. 構成と interaction ルールを定義する

    画面リズム、レイアウト密度、typographic lockup の配置、 ナビゲーション、motion、state の振る舞いを固定します。

  9. AI らしいズレを防ぐ制約を追加する

    根拠のない広すぎる余白、装飾的な gradient、glass 表現、 勝手なイラスト表現を防ぎます。

  10. 開発者向け HTML を生成する

    Markdown と token table を docs/design-system/index.html にまとめ、 review 候補を docs/design-system/review.html にまとめます。

  11. audit と checkpoint を行う

    source audit、token audit、component audit を実行し、session state に決定事項と未解決事項を残し、実装に進む前に一度止めます。

デザイン原則の抽出

繰り返される判断を見つける

複数の画面や node を比較し、密度、強調、階層、抑制、 contrast、motion、feedback など一貫した判断を探します。

振る舞いとして名付ける

原則は装飾名ではなく product behavior として書きます。 例として「dense lists stay readable」は「compact UI」より判断に使えます。

実装ルールへ変換する

各原則は token、component、layout、state、将来の UI に使える implementation rule に落とし込みます。

不確実性を残す

根拠が不足している場合は medium または low confidence として記録し、何を確認すれば確定できるかを書きます。

なぜ抽出するのか

原則が判断を揃える

まだ token や component がない新しい UI でも、agent が同じ判断モデルで設計できます。

根拠が推測を防ぐ

すべてのルールを画像、Figma node、route、source file に結びつけ、 重複 source を確認してから confidence を上げます。

token がずれを防ぐ

ref -> sys -> comp を守ることで、 生値、意味、component 固有の判断を分離できます。近い値の review により、偶発的な重複も防げます。

棚卸しが重複を防ぐ

似た component を作り直すのではなく、意図的に再利用または拡張します。

HTML が引き継ぎを助ける

開発者は、仕様、token、component spec を 1 つの読みやすい画面で確認できます。

出力の約束

編集する source of truth

design-system/*.md と tokens/*.css が編集対象の原本です。

読むための layer

docs/design-system/index.html は原本から生成される 開発者向けの閲覧ページです。docs/design-system/review.html は重複 source、近い token、類似 component をまとめます。

agent への引き継ぎ

Claude Code、Cursor、Codex は同じ仕様、token ルール、 anti-AI 制約、checkpoint を参照します。

品質 gate

source audit、token audit、近い値の判断記録、session-state 更新により、 別プロジェクトでも同じ流れを再現できます。

Extract 流程與目的

這個 skill 會把圖片、Figma URL、專案資料夾與 vibe-coded prototype 中的視覺與程式線索， 整理成未來 AI 和開發者都能共同依循的設計系統規範。

Extract 流程

  1. 盤點輸入來源

    找出 screenshots、圖片輸出、Figma URL、Variables、畫面路由、 Storybook、CSS、token 檔案、vibe project 的 keep/ignore notes、 rendered browser captures 與既有 agent 規則，並用 source fingerprint 先檢查重複輸入。

  2. 建立 evidence map

    記錄每個設計判斷的來源、觀察區域、可重複模式、 影響的 token 或 component、source fingerprint，以及信心等級。

  3. 萃取設計原則

    將反覆出現的 evidence 轉成 5-7 條產品設計原則， 每條都包含命名、觀察依據、實作規則與信心等級。

  4. 萃取設計基礎

    從色彩、字體、文字組合、間距、密度、圓角、層次、圖像、 資料呈現與狀態語言，定義產品的視覺個性。

  5. 建立 token 架構

    把原始值放在 reference token，把語意角色放在 system token， 把 component slot 放在 component token。色階以 100 作為最亮、0 作為最暗；遇到很接近的值時，先確認要合併或保留拆開。

  6. 盤點 component

    找出重複出現的 UI、layout、graphic 與 typographic 模式， 並標記為 extracted、planned、blocked 或 out-of-scope。 遇到相似 component 時，用 fingerprint 與視覺對照圖協助判斷。

  7. 抽出 component spec

    針對高價值且可重用的 component，整理 anatomy、variants、 states 或 display modes、accessibility 與 token slots； evidence 支持時也包含 text lockup。

  8. 定義版面與互動規則

    固定頁面節奏、排版密度、文字組合擺放、導覽模式、動效期待 與狀態行為，讓後續實作不偏離產品語氣。

  9. 補上 anti-AI style rules

    防止 AI 自動加入沒有根據的巨大留白、裝飾漸層、玻璃感卡片、 或不符合參考畫面的插畫風格。

  10. 產生開發者 HTML

    將 Markdown 規範與 token tables 產生成 docs/design-system/index.html，並將 review 候選項目產生成 docs/design-system/review.html。

  11. 執行 audit 並 checkpoint

    檢查 source duplicate review、token 繼承與 component similarity review、更新 session state、列出未決問題，並在進入產品實作前暫停確認下一步。

設計原則怎麼萃取

找出反覆出現的選擇

比對多個畫面或 Figma nodes，找出一致出現的密度、強調、 階層、克制、對比、動效與回饋方式。

用產品行為命名

原則不是裝飾形容詞，而是可判斷的產品行為。 例如「高密度列表仍需易讀」會比「使用緊湊 UI」更可執行。

轉成實作規則

每條原則都要能指導 tokens、components、layout、states 和未來 UI 建議，避免只停留在抽象描述。

保留不確定性

如果 evidence 不夠完整，就標記 medium 或 low confidence， 並記錄還需要哪個來源才能確認。

為什麼要做這些 extract

設計原則讓判斷一致

當新的 UI 情境還沒有既有 token 或 component 可套用時， 原則可以讓 AI 和開發者用同一套判斷模型延伸設計。

Evidence 防止 AI 猜測

每個規則都能追溯到圖片、Figma node、route 或 source file， 且重複來源會先被審查，避免把同一份證據誤算成多份。

Tokens 防止樣式漂移

嚴格維持 ref -> sys -> comp， 可以把原始值、語意角色和 component 決策分清楚；近似 token review 則避免無意義的重複。

Component inventory 防止重複建造

先確認既有模式，再決定重用、延伸或新增 component， 避免產生多個相似但不一致的版本。

HTML 讓交付更容易理解

開發者可以從單一頁面瀏覽規範、token、component spec 與開放問題。

輸出約定

Source of truth

design-system/*.md 與 tokens/*.css 是可編輯的規範原始檔。

閱讀層

docs/design-system/index.html 是由原始檔產生的 開發者閱讀頁面；docs/design-system/review.html 則彙整重複 source、近似 token 與相似 component。

AI agent handoff

Claude Code、Cursor、Codex 都應該讀取同一套規範、token rules、 anti-AI constraints 與 session checkpoint。

品質關卡

透過 source audit、token audit、近似 token 決策和 session-state 更新， 讓 extract 流程能在不同專案中重複使用。

這份 HTML 是 skill 本身的流程說明；每次實際 extract 後產出的 docs/design-system/index.html 則是該專案的設計系統閱讀文件。

Source files 仍然是 Markdown 與 CSS tokens。這個頁面是執行 Claude Code、 Cursor 或 Codex skill 前，用來理解 extract workflow 的可攜式導覽。
