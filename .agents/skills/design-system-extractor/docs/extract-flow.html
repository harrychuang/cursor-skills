Developer Guide

把參考畫面整理成可執行的設計系統

這一頁用開發者視角說明 extractor 做什麼、何時需要停下來 review、 以及最後會留下哪些檔案。目標是讓接手的人能快速判斷： 現在該讀 evidence、補 tokens、整理 component，還是進入 checkpoint。

看流程 開啟簡報版

What it does

Extractor 的工作不是改 UI，而是先建立可信任的規範

它把 screenshot、Figma、專案程式碼和既有 token 轉成可追溯的 design-system package。除非明確要求，產品 UI 實作會留到 checkpoint 之後。

輸入

圖片、Figma URL / exports / variables、prototype 或 project folders。

處理

建立 evidence map，萃取 principles、tokens、components 與 interaction rules。

輸出

Markdown 規範、CSS tokens、HTML docs、review queue 與 audit 結果。

Five steps

核心流程：先證據，再規範，最後才交付

對一般開發者來說，只要記住這五步：收集來源、整理證據、建立 token、 盤點 component、產生文件與 audit。中間遇到重複或近似項目時，不直接猜測。

01

收集來源

列出 screenshot、Figma node、route、CSS、Storybook 和既有規則。

02

建立 evidence

每個設計判斷都要能追到來源、狀態、區域與信心等級。

03

整理 tokens

維持 ref -> sys -> comp，近似值先進 review。

04

盤點 components

用 fingerprint 判斷要 merge、做 variant，或保留成獨立元件。

05

文件與 audit

產生閱讀頁、review queue，執行 source / token / component audit。

  • 設計原則 從反覆出現的視覺判斷萃取，不把單一畫面的偶發樣式當成規範。
  • Token 架構 Reference token 存 raw value；system token 存語意；component token 存元件 slot。
  • Component spec 包含 anatomy、variants、states、accessibility、token contract 和 visual evidence。
  • Checkpoint 更新 SESSION_STATE.md，列出 open questions，停下來等下一步。

Review gates

三個地方不能自動合併，也不能靜默新增

這些 review 是為了避免 token sprawl、重複證據和相似元件越堆越多。 如果 audit 找到問題，先記錄決策，再繼續。

Source

重複來源

同一張圖、同一個 Figma node、同一路由狀態不能被重複算成多份 evidence。 決策是 reuse、ignore duplicate 或 keep distinct。

Token

近似 values

很接近的顏色、spacing、radius、type 或 motion 值要確認 merge 還是 keep distinct。色階固定為 100 最亮、0 最暗；audit 也會檢查 system / component token 的 exact alias duplicate 和 usage-aware 近似用途。

Component

相似元件

新候選元件如果像既有元件，需要比較 purpose、behavior、anatomy、 states 和 token contract。component audit 會自動比對 inventory 與 component specs 的 fingerprint，再要求記錄 merge、variant、distinct 或 blocked。

Files

最後應該留下的檔案

Markdown 和 CSS 是 source of truth；HTML 是開發者閱讀層。 review 和 audit 結果要能讓下一個 agent 或開發者接手。

檔案 用途
design-system/DESIGN_EVIDENCE_MAP.md 記錄來源、fingerprint、證據和 duplicate source review。
design-system/TOKEN_ARCHITECTURE.md 說明 token 分層、色階方向和 near-token 決策。
design-system/COMPONENT_INVENTORY.md 盤點元件狀態，記錄 component similarity review。
tokens/*.css 保存 ref、sys、comp 三層 token，供後續 UI 實作使用。
docs/design-system/index.html 把規範、component specs 和 token 表整理成可閱讀的開發者文件；文件殼支援繁中、英文、日文切換。
docs/design-system/review.html 集中顯示重複來源、色階問題、近似 token、usage-aware token review 和相似 component 的 review queue。
design-system/SESSION_STATE.md 記錄目前階段、audit 結果、未決問題和下一步 prompt。

Template package

初始化後應該依照 template 的順序填寫

assets/design-system-template/ 是每個專案的起始包。真正的 extract 工作不是只跑 script， 而是先把這些 Markdown 和 CSS token 檔案填完整，再用 script 產生閱讀層和檢查缺口。

順序 要填的內容
1. Evidence DESIGN_EVIDENCE_MAP.md：source inventory、fingerprints、duplicate source review 和 evidence rows。
2. Principles DESIGN_PRINCIPLES.md：5-7 條從參考來源萃取出的產品設計原則，每條要有 evidence、implementation rule、do / don't。
3. Foundations DESIGN_ELEMENTS.md：色彩、字體、spacing、shape、elevation、iconography、imagery；同時標記近似值。
4. Tokens TOKEN_ARCHITECTURE.md 與 tokens/*.css：建立 ref / sys / comp，記錄 near-token decisions。
5. Components COMPONENT_INVENTORY.md 和 components/*.md：填 inventory、fingerprint、similarity review、component token contract。
6. Composition PAGE_COMPOSITION_RULES.md、INTERACTION_STATES.md、ANTI_AI_STYLE_RULES.md：固定版面、狀態和 anti-drift 規則。
7. Checkpoint SESSION_STATE.md：更新完成項目、review 結果、audit 結果、open questions 和下一步 prompt。

Scripts

5 個 script 各自負責不同層級

這些 script 不會替你做設計判斷；它們會把缺少的 evidence、未決 review、token 繼承問題和 component 重複風險暴露出來，讓 checkpoint 可以被可靠驗證。

Script 實際檢查或產出
generate_docs_html.mjs 產生 docs/design-system/index.html，渲染 core docs、extra docs、component specs、token tables、resolved token values、color swatches；也會複製 design-system/assets/ 到 generated docs，並提供繁中 / 英文 / 日文文件殼切換。
generate_review_html.mjs 產生 docs/design-system/review.html，彙整 duplicate source rows、color scale issues、near colors、near numbers、exact sys/comp aliases、usage-aware token pairs 和 component similarity rows。
audit_sources.mjs 檢查 DESIGN_EVIDENCE_MAP.md 是否有 Source Inventory、source fingerprint、重複 fingerprint / path-state group，以及 unresolved duplicate source decision。
audit_tokens.mjs 檢查 token import order、ref / sys / comp 命名與繼承、ref 色階 100 -> 0、near reference colors/numbers、exact sys/comp alias duplicates、usage-aware sys/comp near token pairs。
audit_components.mjs 檢查 inventory、similarity review table、visual reference 是否為 Figma preview / screenshot crop / labeled fallback、component specs 是否有 Component Fingerprint，並自動比對 inventory/spec fingerprints 找出相似 component pair。

Commands

開發者最常需要跑的指令

產出文件後，跑三個 audit。若 strict mode 失敗，通常代表還缺 review 決策、fingerprint、token inheritance 或 component fingerprint。 

node skills/design-system-extractor/scripts/generate_docs_html.mjs .
node skills/design-system-extractor/scripts/generate_review_html.mjs .
node skills/design-system-extractor/scripts/audit_sources.mjs . --strict
node skills/design-system-extractor/scripts/audit_tokens.mjs . --strict
node skills/design-system-extractor/scripts/audit_components.mjs . --strict

這份頁面是 skill 自身的流程說明；實際專案的文件會產生在該專案的 docs/design-system/ 目錄。

Source files remain Markdown and CSS tokens. This guide exists so Claude Code, Cursor, Codex, and human developers can follow the same extraction workflow.
