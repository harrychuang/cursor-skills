從畫面
到可交付的產品。

這份說明收錄 repo 根目錄的 24 個 skills。每個 skill 負責一段工作：萃取設計系統、建成 Storybook、做出可點的原型、寫進產品，或把畫面落差修回去。

一條主線

多數產品可以照這個順序走。前面的產出是後面的輸入。做 UI 的時候，設計治理會一直在旁邊，先找既有 token 與元件。

  1. 01 萃取設計系統 截圖、Figma、現有 App
  2. 02 建成 Storybook token、元件、stories
  3. 03 原型與交接 PRD、流程、資料契約
  4. 04 實作畫面 Web，或 iOS / Android
  5. 05 接上真資料 API、登入、儲存
  6. 06 對齊畫面 先出報告，再修
空資料夾 從截圖或 Figma 開一個新專案 已經有專案 把一張畫面拆成可重用元件 還在 Figma 把寫死的數值做成變數 還在 Figma 把還沒元件化的畫面做成元件 要給人看流程 做一張可拖曳的 UI Flow 要交給工程 做出原型和交接文件 要寫進產品 用交接文件實作 Web 要寫進 App 用同一份交接實作 iOS 或 Android 畫面不一樣 對著設計把落差修掉 要開會 把想法收成四頁提案 簡報已經有了 逐頁檢查結論和證據 同一件事會再做 收成可重跑的自動化

設計系統

先看來源長什麼樣子，抽出可重用的規格，再做成 Storybook。寫畫面之前先過治理。

create-design-workspace

開一個新的交付專案

從 UI 截圖或 Figma URL 建出一整個前端工作區，再沿著 Storybook、token 與視覺對齊把實作做完。產生的工作區可以給 Cursor、Claude Code 和 Codex 用。

什麼時候用

資料夾是空的，你要從參考圖或 Figma 開始做一個新產品。

怎麼呼叫

Use $create-design-workspace to bootstrap a new UI-to-code workspace in this empty folder from screenshots or a Figma URL and carry it through implementation.

  • 接著萃取設計系統
  • 只有一張圖時改用這個

design-system-extractor

萃取設計系統

從截圖、品牌參考、Figma、Figma Variables、現有 Web 或 iOS / Android 專案、模擬器截圖、原型程式，抽出可重用的設計系統規格。產出包含有證據的設計原則、設計元素、token 架構、元件清單、元件 token，以及給工程看的靜態 HTML 說明。實作產品之前會先停在檢查點。

什麼時候用

你手上有畫面來源，下一步是先把它變成一份設計系統。

怎麼呼叫

Use $design-system-extractor to extract a reusable design-system package and static HTML docs from screenshots, a Figma URL, rendered captures, or an existing app project.

  • 接著建成 Storybook

design-system-governance

設計治理

做任何 UI 之前，先找出這個專案既有的 token 命名、格線、動畫與共用元件，再依那些規則寫。缺 token 或缺共用元件時會停下來問，而不是直接硬寫數值或複製一份新元件。也管動畫、介面文案與 Storybook 狀態。

什麼時候用

正在做元件、版面、頁面、token 或 Storybook。提到設計 token、寫死的樣式、元件重用、動畫或介面文案時也用它。Web 與原生實作都會跟著它走。

怎麼呼叫

Use $design-system-governance before building UI. Discover tokens, grid, motion, i18n, and shared components first, and stop for approval before creating missing ones.

資料夾 ds-to-storybook　·　呼叫 $design-system-to-storybook

建成 Storybook

把已經萃取的設計系統做成這個專案框架原生的 Storybook：基礎、共用元件與 stories。它會先判斷 app 根目錄、renderer、建置工具與檔案慣例，依相依順序做元件，並同步元件文件。附帶 Figma export addon，以及把 Storybook 畫面送回 Figma 的 Code To Design importer。

什麼時候用

設計系統規格已經有了，下一步是在現有或新的前端專案裡做出 token 支撐的元件庫。它沿用專案既有的框架，React、Vue、Angular、Svelte 或 Web Components 都可以。

怎麼呼叫

Use $design-system-to-storybook to inherit this repo's framework and conventions, then build token-backed Storybook components and docs.

  • 接著做產品原型
  • 有 Figma 證據時要出對齊報告

screenshot-to-storybook

從一張畫面做成元件

把一張 UI 截圖、mockup 或 Figma 匯出，先盤點可重用的積木，擴充 Storybook 或專案的元件目錄，再用這些有文件的元件組出產品畫面。

什麼時候用

專案已經在了，你要依一張圖實作，而且希望畫面來自既有元件。

怎麼呼叫

Use $screenshot-to-storybook on this screenshot. Inventory the UI blocks, extend the component catalog first, then compose the screen.

原型與實作

原型負責把產品說清楚並留下交接。實作負責把交接寫進 Web 或 App。接真的 API 是再下一棒，而且不動 UI。

prototype-storybook-flow

可拖曳的 UI Flow

在 src/pages/prototypes 做出以 PRD 為起點的 Storybook 原型：文件、有型別的路由與轉場、固定的 fixtures，以及一張看得到真實畫面的流程圖。節點可拖、有虛線箭頭、可縮放。另外有一則給 Figma 匯出用的 flow story，輸出的 JSON 可以再進 Figma。

什麼時候用

你要把一個產品想法變成 PRD 加 UI Flow，或更新既有原型的流程，讓人一眼看出每個畫面怎麼連到下一個畫面。

怎麼呼叫

Use $prototype-storybook-flow to create a PRD-led Storybook prototype with typed UI Flow metadata, real route previews, animated dashed arrows, and draggable nodes.

  • 需要完整交接文件時用這個

storybook-product-prototype

原型與工程交接

把產品想法做成可點的 Storybook 原型，並交出工程能接著做的文件：PRD、UI Flow、Data Spec、Production Handoff、Acceptance。流程有型別，fixtures 是固定的，資料契約先寫清楚，先不接真的後端。可選的 Prototype Inspector 用來看 Story、Docs、UI Flow 與 Data。

什麼時候用

設計要交給工程或下一個 AI 實作。Web 與 App 都可以從這裡開始。它接在 Storybook 元件庫之後，也可以單獨從一個產品想法開始。

怎麼呼叫

Use $storybook-product-prototype to create the PRD, data spec, UI Flow, production handoff, and a clickable Storybook prototype.

  • Web 實作
  • iOS / Android 實作

frontend-product-implementation

實作 Web 產品

依 PRD、UI Flow、UI Spec、Data Spec、Acceptance、Implementation Guide 與 Production Handoff 實作前端。它先看目標專案的框架與架構，沿用已經清楚的技術棧。畫面用 mock DataSource 與固定 fixtures，真的 API、登入與儲存留給下一棒。

什麼時候用

從 0 做一個 Web 產品、在既有產品加一個路由或功能，或把 Storybook 原型交接寫成正式程式。做 UI 前先走設計治理。

怎麼呼叫

Use $frontend-product-implementation to resolve this repo's runtime and implement the feature from the handoff docs, with design-system governance.

  • 接著接真資料
  • 目標是 App 時改用這個

native-app-implementation

實作 iOS 與 Android

用同一套交接文件實作原生 UI：iOS 是 SwiftUI、Xcode、SPM；Android 是 Jetpack Compose、Gradle、Kotlin。它沿用 App 既有架構，套用設計治理，把假資料和已確認的傳輸 DTO 分開，並留下 mock DataSource 給下一棒替換。

什麼時候用

Storybook 交接的目標是原生 App，或要把已確認的導航、動效、TOKENS.json 寫成 SwiftUI 或 Compose。

怎麼呼叫

Use $native-app-implementation to implement this iOS SwiftUI or Android Compose feature from the prototype handoff, following design-system governance.

  • 接著接真資料

api-data-integration

接上真的資料

在已經組好的 DataSource 接縫後面，把 mock adapter 換成真的 API client、登入與 session、快取、儲存與環境設定，並用契約測試證明對映。它只處理資料接線。UI、路由、元件與 token 留在原地。

什麼時候用

功能已經能以 mock 跑起來，交接文件指定了資料整合的負責人，而且傳輸契約與 DTO 對到 UI 的方式已經確認。

怎麼呼叫

Use $api-data-integration to replace the mock adapters with real API clients and contract tests, without changing UI behavior.

Figma

這些 skill 改的是 Figma 檔，或把 Figma 上的修改分回流回程式。只做變數、做成元件、裝清理自動化，是三件不同的事。

figma-m3-variables

建立與套用變數

用 Material Design 3 的三層繼承（Ref → Sys → Comp）建立、套用、稽核 Figma Variables。涵蓋顏色、字級與 Text Styles、形狀、間距、尺寸、描邊、透明度，以及海拔與 Effect Styles。

什麼時候用

要把畫面上寫死的數值變成 token、建立一套變數、把變數綁到選取或整頁，或稽核命名與 alias。這一步不建立元件。

怎麼呼叫

Use $figma-m3-variables to turn the hardcoded values in this Figma node into Ref, Sys, and Comp variables and bind them.

  • 畫面還不是元件時用這個

figma-componentize

把畫面做成元件

找出 section、frame 或單一元素裡還沒用元件組起來的 UI，由下往上做成元件、variants（Style、Size、State）與 component properties，放在 Components 頁。顏色、字級、圓角、間距與海拔會透過 figma-m3-variables 的 Workflow F 做成變數，再把原本的圖層換成 instance，並確認外觀沒有變。

什麼時候用

設計師貼上一塊還沒元件化的 Figma，希望建成元件並換上 instance。只要把數值改成變數、不建元件時，改用 figma-m3-variables。

怎麼呼叫

Use $figma-componentize to turn this Figma section into components and variants, tokenize them, and replace the originals with instances.

figma-storybook-sync

把 Figma 的修改分回流

元件或頁面曾經用 Storybook 的 Figma export addon 送進 Figma，之後又在 Figma 裡改過。這個 skill 用三方比較——上次同步的基準、現在的 Storybook 匯出、現在的 Figma——列出哪些 stories 要更新，以及每一筆差異該往哪裡走。token 差異回到設計系統萃取，視覺差異交給畫面修復，結構差異留給人處理。它自己不改產品元件、token CSS 或元件規格。

什麼時候用

Figma 已經被改過，你想知道改了什麼、改動方向，以及每一筆該怎麼流回程式。

怎麼呼叫

Use $figma-storybook-sync to compare the synced baseline, the current Storybook export, and the current Figma state, then route each change.

  • 視覺差異交給修復
  • token 差異回到萃取

design-automation-hub

安裝 Figma 清理自動化

把 Design Automation Hub 裝進一個明確的目標 repo：Figma plugin、本機 Coordinator、專案綁定，以及配套 skill figma-design-automation。執行仍交給同一個 checkout 裡的 agent-automation，不另外做一套 runner，也不覆蓋無關的專案設定。

什麼時候用

要在某個專案安裝、檢查、更新或驗證這套 Figma 清理流程。目標 repo 需要已有有效的 .agent-automation/config.json；還沒有時，先用 agent-automation 建立契約。

怎麼呼叫

Use $design-automation-hub to preview, install, or update Design Automation Hub in this repository and report the Figma manifest handoff.

  • 先有自動化契約

視覺與平台

報告負責留下證據。修復負責改畫面，而且從 token 與共用元件開始改。跨平台交接與摺疊螢幕是另外兩件事。

ui-pixel-alignment

像素對齊報告

把做好的 UI 和設計或程式參考比對，產出帶截圖的像素對齊報告。參考可以是 Figma frame、設計匯出、截圖，或另一個平台的原始碼。報告會指出落差、嚴重度與歸屬。預設只記錄，不改實作。

什麼時候用

設計對實作的視覺 QA、跨平台對齊稽核、Figma 比較，或在修之前要一份可以交給別人的證據。

怎麼呼叫

Use $ui-pixel-alignment to compare this design reference with the implemented UI and generate a pixel alignment report.

  • 要修的時候接這個

資料夾 ui-visual-parity　·　呼叫 $ui-compare-to-reference

修掉視覺落差

把做好的 UI 和參考比較，然後動手修。參考同樣可以是 Figma、截圖，或另一個平台的程式。修復順序是 token 與主題、共用元件、元件 variant，最後才是畫面自己的樣式。平台之間本來就該不一樣的地方會留下來。

什麼時候用

App 或 Web 和設計不一致，或要把一個畫面從 Web 對到 React Native、Flutter、iOS、Android，而且你要的是修好，不只是一份報告。

怎麼呼叫

Use $ui-compare-to-reference to compare this screen with the reference and fix the visual drift, starting from tokens and shared components.

cross-platform-parity

先端到次端的交接

一個平台的功能合併進整合分支之後，從合併 diff 與原始碼產出給另一個平台的交接包：凍結點、變更清單、畫面狀態矩陣、視覺數值、字串 id、行為契約、API / remote config / 事件 key、共用元件影響，以及已宣告的平台差異。次端可以在實作前與實作後依這包做審計。專案路徑來自一份 JSON profile。

什麼時候用

iOS 要交給 Android，或反過來，次端必須對齊已經做好的實作。它不做功能規劃，也不做單一平台裡的一般開發。

怎麼呼叫

使用 $cross-platform-parity：先讀專案 profile，對指定功能的先端合併提交產出交接包，或對既有交接包在次端做審計。

  • 視覺細節可另出像素報告

ios-foldable-adaptation

摺疊 iPhone 適配

把 iOS App 適配到可摺疊的 iPhone Duo：外螢幕 466×678 pt，內螢幕 951×669 pt，中間有系統直欄。流程包含盤點依賴螢幕尺寸的版面、一份設計師回答的顯示風格問卷、版面規則、在 Lego 產線框架或一般 UIKit / SwiftUI 上實作、用模擬器自動開合截圖，以及一份前後對照的 HTML 報告。

什麼時候用

提到 iPhone Duo、摺疊、直欄、開合、內螢幕或外螢幕，或只要這個產品在 Duo 上的截圖、QC 報告或計畫。一般 iPad 多工不在這裡。

怎麼呼叫

Use $ios-foldable-adaptation to inventory this iOS app for iPhone Duo, apply the fold layout rules, and produce a before/after QC report.

自動化

自動化負責排程、執行與留下完成證明。看板只讀磁碟上已經有的結果，不會自己啟動 runner。

agent-automation

多代理自動化

為一個 repo 建立可重跑的自動化契約，再用 Claude Code、Codex、Cursor 或其他 headless CLI 依序執行、續跑與檢查。設計師可以用白話描述想自動化的事，例如把準備好的 Figma 元件做成 Storybook。專案特有的行為寫在專案契約與配套 skill，不寫進共用 runner。

什麼時候用

同一條設計到工程的流程會重複做，需要可稽核的 fallback 與完成證明，或已經有 .agent-automation/config.json 要跑或續跑。

怎麼呼叫

Use $agent-automation to set up automation for this repo. I want ready-for-dev Figma components built into Storybook.

  • 在契約上加 Figma 清理
  • 看這條管線走到哪

automation-pipeline-board

一條管線的看板

產出一份給設計師看的靜態 HTML。它說明這條設計到工程的管線在做什麼、哪些階段已經有產出或通過驗證、哪些交接完成、堵住或過期，以及有幾件決定在等設計師。所有說法來自磁碟上的檔案，以及 agent-automation 留下的 run summary。沒有伺服器，也不會啟動任何 runner。

什麼時候用

不想讀 Markdown 或 JSON，只想一眼知道這個專案的萃取、設計系統與 Storybook 走到哪，以及下游是不是在上游變更之前就做好了。

怎麼呼叫

Use $automation-pipeline-board to render a self-contained HTML board of this repo's automation stages, handoffs, and waiting designer decisions.

automation-portfolio

很多專案的總覽

把多個專案的管線看板收成一頁靜態 HTML。每個專案一張卡：現在在哪個階段、為什麼停住、有哪些決定在等人，以及連到該專案自己的看板。某一個專案失敗會變成一張錯誤卡，整批仍會做完。它不修改那些專案。

什麼時候用

你同時看好幾個跑設計到工程自動化的專案，想用一頁回答「誰在哪、誰被堵住」。

怎麼呼叫

Use $automation-portfolio to render one HTML overview of every tracked project's pipeline status.

storybook-tools

Storybook 工具頁

把一套通用的 Tools 頁裝進任何 React + Vite 的 Storybook。目前有兩個：Component Coverage Analyzer 用 UI 圖或 PRD 對元件目錄做覆蓋率報告；Component Timeline 依 git 裡元件第一次出現的時間排成時間軸，並顯示 live story。安裝時會一併放入配套 skill component-coverage-analyze 與 component-coverage-implement。

什麼時候用

要在 Storybook 側欄看到工具頁、元件覆蓋率或元件時間軸，或把以前只裝了覆蓋率的版本更新到整套工具。

怎麼呼叫

Use $storybook-tools to install the Storybook tools suite into this React + Vite Storybook.

automation-task-board 在根目錄，但它是任務看板應用，沒有 SKILL.md。控制平面與 worker 的安裝方式寫在該資料夾的 README。看板執行時會呼叫 agent-automation 的 runner，以及管線看板的狀態腳本。

簡報

一份負責把材料收成提案，一份負責審查已經寫好的簡報。審查用的規則在獨立檔案裡，可以單獨改。

executive-proposal

產品價值提案

把主題、會議記錄或一堆資料，整理成白話、結論先行的產品提案。以 UI/UX 產品總監的角度說明使用者問題、設計選擇與產品價值，並補找案例與來源，再詢問可以引用的截圖或連結。

什麼時候用

新功能發想、設計提案、主管報告，而你還沒有一份可以上台的簡報。

怎麼呼叫

使用 $executive-proposal，將以下內容整理成白話的四頁產品提案，說明產品價值、補找相關案例與來源，並詢問需要的截圖或連結：

  • 寫完後可以拿去審查

presentation-content-review

逐頁審查簡報

依一套可改版的規則檢查每一頁：標題是一個結論（觀點加行動），副標補上理由，每一頁有 1 到 3 個能支撐該結論的證據，並寫明來源。輸出總評、逐頁判定、必改清單、改寫建議與待補證據。沒有的證據不會被編成有。

什麼時候用

設計提案、主管報告或產品簡報已經有稿，要先審再改。你明確要求時，它也可以依同一套規則改寫或起草。

怎麼呼叫
