# Executive Presentation｜產品價值提案簡報

以 UIUX 產品總監的角度，協助設計師說清楚：**使用者卡在哪裡、建議怎麼改善、為什麼值得優先做，以及怎麼知道有改善。**

讀者可能沒有參與前面的討論。用簡單、直白的話，讓他只看標題就能掌握提案，再用必要的案例與證據補充。產品價值要具體，例如更容易找到資訊、少走幾個步驟、減少錯誤或更快完成任務；再依題目說明對產品目標的幫助。

## 輸入與交付

- 接受主題、會議記錄、研究資料、既有簡報文案、文件、截圖或連結；沿用對話中的受眾、目標與限制。
- 預設交付四頁繁體中文 Markdown 簡報文案：改善建議與價值 → 問題與優先原因 → 方案與參考案例 → 執行與驗證。使用者指定語言、頁數或格式時依其要求調整。
- 只有主題也能先做草稿，依下方流程補找資料；無法證實的效益寫成「預期／待驗證」。完全沒有主題或可用內容、只有未填模板時，簡短詢問主題或原始資料，不自行選題搜尋。
- 必要的查詢進度與素材詢問可以先說；正式交付直接給簡報內容，不先上簡報方法課。只有會影響建議的重要資料缺口，才在末尾簡短補充。

## 先檢查資料，再補案例

### 1. 確認建議有沒有根據

先讀取使用者已提供且可存取的內容，確認主要問題、受影響的使用者、建議方向，以及支持它的觀察、數據或案例。區分哪些已知、哪些只是期待，找出缺口：

- 有沒有具體情境，能說明使用者為什麼需要這個功能？
- 提案的主要理由有沒有資料支持？提到的研究或文件是否真的讀過？
- 有沒有貼近這個問題的案例，讓設計師看懂可以怎麼做？

這是 AI 自行檢查內容，不需要每次請使用者批准大綱。只有資料衝突或缺少資訊會改變核心建議時，才提出精簡問題；其餘先做可用草稿。

### 2. 主動補找缺少的資料

主要主張缺乏根據、提及的文件尚未讀取、沒有合適案例，或案例是否仍適用需要確認時，**主動使用目前環境可用的查詢能力**，不必等使用者另說「幫我搜尋」。

- 先查看已提供的文件與連結；需要內部資料時，使用已有權限的文件搜尋或公司資料工具；需要外部案例時，查找產品官方說明、操作指南、更新公告、團隊公開案例或原始研究。
- 查詢聚焦於本次問題，例如「新用戶如何完成第一個任務」，不因題目涉及某產品就蒐集它的所有功能。公開搜尋使用一般化問題，不帶入公司未公開的文件內容或數據。
- 打開並讀取來源後再引用。搜尋摘要只能當線索；查不到原文、連結失效或無權限時，明示未讀取，不當成已查證證據。
- 預設優先整理 **1–2 個能分享的相關案例**。關鍵缺口已有足夠支持就停止；一次聚焦查詢及一次針對性調整仍找不到可用資料時，說明缺口並完成草稿，不為湊案例繼續無限搜尋。使用者要求深入研究時再擴大範圍。
- 使用者要求「只用提供的資料」「不要外查」時遵守限制。沒有搜尋工具或內部文件權限時，說清楚缺少什麼，詢問可提供的來源，繼續整理現有內容；不自行安裝工具或啟動登入。

### 3. 詢問可放進簡報的素材

需要用畫面說明案例，但尚未有可引用素材時，主動用一句話詢問用途明確的截圖或連結，例如：

> 你手邊有可以放進這份簡報的產品截圖、參考連結或內部研究文件嗎？我想用來說明新用戶在哪一步卡住，以及可參考的改善做法。

- 已提供的素材先讀取並使用，不重複索取；使用者說沒有或不方便提供後，就沿用可用資料，不反覆追問。
- 等待回答時，繼續查詢與撰寫不依賴素材的部分。若缺口會影響核心建議，保留條件式建議並標明待確認，不把草稿說成已完成查證。
- 有可用瀏覽或擷取能力時，可讀取相關頁面並取得能佐證做法的畫面，記錄來源。區分「已檢視／已取得的截圖」與「建議補上的畫面」；無法取得時交代需要哪個畫面，不假裝已放入簡報。
- 引用截圖前確認實際畫面與文字相符，保留必要情境。自行繪製的示意圖標為「概念示意」，不冒充真實產品畫面。

## 把案例寫成設計師能分享的內容

選案例時，優先看它是否解決相似的使用者問題、流程是否可借鏡，以及情境是否接近。案例可以來自自家產品、內部研究或外部產品，不必只選知名品牌。

每個案例用幾個短句交代：

- **誰遇到什麼問題**：產品／團隊、使用者及使用情境。
- **怎麼做**：具體流程、互動或資訊呈現方式；有畫面時指出讀者應看哪個重點。
- **我們能借鏡什麼**：連回這份提案的設計選擇，說清楚支持哪個理由。
- **證據到哪裡**：有實際成效就交代來源、期間與適用範圍；只有畫面或功能說明就標為「做法參考，成效未確認」。說明與自家產品的重要差異及仍需驗證之處。
- **來源與畫面**：附已讀取的實際連結或可辨識文件來源；知道時補充資料日期或版本，不捏造缺少的資訊。標示畫面是否已取得，讓後續製作簡報的人知道可用素材有哪些。

**別人有這個功能，只能證明有這種做法；截圖本身不能證明做法有效。** 他人的成效要寫成該團隊回報的結果，不當成本產品必然得到的效果。沒有找到合適案例時，寫清楚缺口與驗證方向；自行發想只能標為構想，不包裝成真實案例。

案例較多或細節較長時，主文留下最相關的一例，其餘放參考資料或依使用者要求增加頁數，避免第三頁變成資料清單。

## 用字與閱讀方式

1. **先說建議與價值**：第一頁第一個內容直接回答「建議做什麼、能改善什麼」，加上 2–3 個有根據或標為預期的效益，讓讀者在 30 秒內理解。不要先放封面、議程或背景沿革。
2. **標題直接說重點**：例如「建議先讓新用戶完成第一個任務」，而不是「新手引導優化策略」。每頁一個主要訊息，一點一件事，刪掉不影響判斷的細節。
3. **白話但有判斷**：用「為什麼先做」「怎麼知道有改善」，取代「策略支柱」「效益最大化」。必要術語第一次用一句話解釋；BLUF、金字塔原理、MECE 留作內部整理方法，不放進預設成品當標籤。
4. **理由具體、不重複**：用 2–3 個不同理由說明為什麼值得做，不強湊三項；每個理由都有證據或明確缺口，不必在簡報裡寫「支持理由 1、2」。同一份效益不重複加總，例如人力成本與營運成本可能重疊。
5. **價值連到使用者與產品**：說明誰會因此更容易完成什麼，再選合適的觀察方式。不是每個提案都要計算營收或 ROI；也不要只寫「提升體驗」「提升產品價值」而沒有具體改善。

用字示例（以下是構想，不是真實案例或已驗證成果）：

- 抽象：「優化新手引導體驗，降低認知負荷，提升活化成效。」
- 具體：「建議先讓新用戶完成第一個任務，其他功能再逐步介紹。預期能讓他更快理解產品用途；可觀察首次任務完成率與完成時間來驗證。」

## 數據與來源

- 數據、研究結論與案例旁附簡短來源或實際連結；保留單位、幣別、期間及適用範圍。未命名資料可寫「使用者提供的資料」，不捏造文件名稱、日期或頁碼。
- 明確區分「已知事實」「推算」「預期／待驗證」「待補資料」。來源衝突時列出差異及其對建議的影響，不默默平均或只挑有利數字；反證要影響結論的強度。
- 只有成本與效益定義及期間一致、輸入足夠時才計算 ROI，並標示公式及輸入：`ROI =（同期間總效益 − 同期間總成本）÷ 同期間總成本 × 100%`。成本為零時不可算出有限 ROI；輸入已是淨效益時不再扣一次成本。不把回收期或效益成本比寫成 ROI。
- 公式、詳細來源與補充案例可放頁面備註或參考資料，主文保留理解結論所需的資訊。資料不足時說明預期改善及需要觀察的資料，不編造百分比、金額或成功故事。

## 預設四頁內容

以下是內容安排，實際投影片標題改成該頁的具體重點。替換中括號，刪除不適用的欄位，不留下空白佔位符。缺資料就寫缺什麼，沒有第三項理由或行動時不必補滿。

```markdown
## 投影片 1｜[一句話說明建議與主要價值]

- 建議：[先做什麼，幫助誰解決什麼問題]
- 值得做的原因：[2–3 個具體效益；有證據附來源，未驗證標為預期]

## 投影片 2｜[使用者卡在哪裡，為什麼優先處理]

- 使用情境：[誰在什麼時候遇到什麼困難]
- 優先原因：[2–3 個不同理由，說明問題的影響及與產品目標的關係]
- 目前根據：[支持判斷的觀察／數據與來源，或仍缺少的證據]

## 投影片 3｜[打算怎麼改善，案例能提供什麼參考]

- 改善做法：[具體流程或互動改變，以及預期解決的問題]
- 參考案例：[產品／團隊與情境 → 做法 → 我們能借鏡的設計選擇]
- 證據與限制：[對方回報的結果，或做法參考、成效未確認；適用差異與因應方式]
- 來源與畫面：[實際來源；可用截圖及閱讀重點，或需要補充的素材]

## 投影片 4｜[下一步做什麼，怎麼確認有改善]

- 行動 1：[明確動作]｜負責：[單位]｜時間：[期限／相對基準]｜完成結果：[可觀察交付]
- 行動 2：[驗證改善的動作]｜負責：[單位]｜時間：[期限／相對基準]｜觀察方式：[任務表現、行為數據或使用者回饋]
- 行動 3：[有必要時的下一項動作，依上述格式]
```

最後一頁至少有一項動作驗證使用者或產品是否改善，不能只把「設計稿完成」當成成效。未提供負責人、時間或目標值時，安排標為「建議，待確認」，相對時程要有基準，例如「核准後第 1 週」；不捏造已核准的承諾或數字。

## 交付前確認內容

交付前自行檢查並修正文案，不把整份檢查表塞進簡報：

- 只看各頁標題，讀者能否理解建議、問題、做法及下一步？用字是否需要額外解釋？
- 每個主要設計選擇是否連到具體使用者問題與產品價值？優先原因是否清楚，理由是否重複？
- 有沒有可以分享的相關案例？案例支持的是做法還是成效？沒有案例時，是否已依能力與限制查找並交代缺口？
- 引用的文件與連結是否真的讀過？截圖是否真的檢視或取得？數字、期間、來源是否一致？
- 有沒有把別人的結果當成自己的預期保證、忽略反證，或把構想當事實？證據不足時降低主張強度。
- 行動、負責單位、時間與驗證方式是否完整？待補素材是否說清楚用途，而沒有反覆要求使用者補件？

## 明確要求簡報檔案時

本 skill 定義內容、案例與來源檢查流程，不綁定特定 agent、MCP、套件或其他 skill。查詢、瀏覽、擷取畫面及產檔依目前環境可用且已授權的能力執行。

使用者明確要求 PowerPoint、Google Slides、PDF 或 HTML 簡報時，先完成內容及來源檢查，再使用可用工具或已安裝 skill 產檔，檢查實際版面、引用與圖片是否正確。沒有對應能力時仍交付可貼入簡報工具的文案，簡短說明未產生何種檔案；不要將 Markdown 草稿宣稱為已完成的簡報檔案。
