## Context

`ui-visual-parity`（frontmatter 名稱原為 `ui-compare-to-reference`，本次統一為資料夾名稱，見「skill 名稱以資料夾名稱為準」）負責「比對參考與實作，並把視覺差異修掉」。上一次升級（2026-08-19）把目測式比對改成量測優先，並加入分層修復的收斂迴圈，解決了「要跑兩次才到位」的問題。這次的目標是提高上限：讓 AI 能把視覺細節修到與參考一致。

目前的做法：

- 兩邊各自整理成一份規格 JSON（15 到 60 個人工挑選的節點），再由 `ui-pixel-align-report` 的比對腳本逐欄位比較，以「欄位收斂率」作為進度。
- 規格格式、擷取說明與比對腳本都放在 `ui-pixel-align-report`。該 skill 不在本 repo（GitHub 上游也沒有），而 design-workspace-starter 的 managedSkills 只會把 `ui-visual-parity` 這一個資料夾同步進 workspace。所以從本 repo 安裝的使用者，預設流程指向的檔案並不存在。

研究階段以實測確認了下列限制（比對腳本為已安裝版本的 `diff_spec.mjs`，預設 policy）：

| 現象 | 實測結果 |
| --- | --- |
| 1px 以內的誤差 | padding 16 對 15、圓角 8 對 7、高度 40 對 41 都判定通過 |
| 行高、字距 | 同尺寸的 Figma 對 web 也歸類為 adaptation，計入收斂率 |
| 一邊沒有值 | 整個欄位跳過且不計入分母；實作沒設行高時不會被發現 |
| 位置 | 完全不比對；多一層包裝把內容往下推 3px 不會被發現 |
| 互動狀態 | 只檢查有沒有 hover 這個鍵，不比對內容 |
| 框線 | 只看上邊；只有下邊框線的分隔線不會被發現 |
| 規格格式沒有的東西 | 漸層、圖示內容與線條粗細、圖片裁切方式、底線、大小寫轉換、placeholder 顏色、`::before` 與 `::after` 都無法表達 |
| 相同畫面的不同寫法 | 全圓角寫成 9999px、用 margin 代替 gap、用 padding 代替固定高度、陰影字串格式不同、`start` 對 `flex-start`、hex 對 hsl，都被回報為偏差 |
| 重複元件 | 名稱相同的列表列全部配對失敗 |
| 最終檢查 | 沒有任何一步比對實際畫面 |

基準測試（兩個測試頁，各自以「只改一處」的方式埋入差異；另有「畫面相同但寫法不同」的陷阱）：

| | 手機錢包頁（36 個差異） | 桌面設定頁（31 個差異） | 合計（67） | 陷阱誤報（6 個） |
| --- | --- | --- | --- | --- |
| 現行流程，照文件原樣執行 | 3 | 4 | 7 | 1 |
| 現行流程，最理想情況（每個元素都被擷取且配對成功） | 19 | 19 | 38 | 5 |
| 原型 | 36 | 31 | 67 | 0 |

數字為「有指出原因」的差異數。現行流程最理想情況下，另有 11 個只看到症狀或被歸為不必修、18 個完全看不到；全部差異同時存在時回報的收斂率仍為 94%。桌面設定頁是在原型完成後才寫的；原型未經調整時在該頁指出原因的是 26 個，其餘 5 個都被疊圖檢查標為差異，之後補上 4 類缺口（偽元素、文字對齊、明確尺寸、原因與結果互相抵銷）才到 31 個。兩頁的「相同頁面」對照組都判定為一致，其中錢包頁的對照組刻意使用不同的元素結構。

原型、兩個測試頁與重跑方式保存在本 change 目錄的 research 資料夾，實作時以它為基礎。上表是研究階段的數字；實作期間基準測試擴充為 72 個差異（錢包頁 37、設定頁 35）與 9 個陷阱，隨 skill 附上的是擴充後的版本。

限制：

- 本 repo 是 skill 的來源，沒有共用的建置或相依套件安裝步驟；skill 會被複製到任意專案與不同的 AI 工具（Claude Code、Cursor、Codex）中使用。
- 設計師是主要使用者；輸出需要能以設計師的語言閱讀（間距、框線、對齊），並指到可修改的位置。
- Figma 端的寫入型工具並非每個環境都有；常見的 Dev Mode MCP 只能讀取。可執行 Plugin API 的工具每次回傳上限為 20kB。
- 本機沒有可供驗證的 Figma 檔；Figma 端腳本只能在取得設計師提供的 frame 之後驗證。

## Goals / Non-Goals

**Goals:**

- AI 每一輪量測都能看到所有設計師看得出來的差異，並得到「該改哪個屬性、改在哪裡」的指示。
- 相同的畫面不論怎麼寫，都不會被回報為差異。
- 一次只需要一個指令就能重新量測，判定結果可由結束碼取得，讓修復迴圈有明確的結束條件。

- 重新命名資料夾：`ui-visual-parity` 這個資料夾名稱維持不變（名稱統一的方向是讓 frontmatter 跟著資料夾，見「skill 名稱以資料夾名稱為準」）。
- 統一 `ds-to-storybook` 的名稱：它有同樣的不一致（frontmatter 名稱為 `design-system-to-storybook`），不在本次範圍。
- 同步家目錄下的已安裝副本與另一個 skills repo：位於本 repo 之外，完成後詢問使用者。

## Decisions

### 量測工具內建在 ui-visual-parity

擷取、比對、疊圖與量測循環的腳本，以及規格格式、分類規則的說明，全部放在 `ui-visual-parity` 資料夾內。

理由：workspace 同步與 README 的安裝方式都只複製單一 skill 資料夾；目前引用的 `ui-pixel-align-report` 不在本 repo，預設流程因此無法執行。修復迴圈每一輪都要重新量測，量測工具與迴圈放在一起最不容易失聯。

替代方案：把 `ui-pixel-align-report` 加進本 repo 並在那裡升級。未採用，因為 workspace 同步清單與安裝說明都要跟著改，而且任何只裝了其中一個 skill 的環境仍然會壞。相容性以資料格式維持：本 skill 仍接受該 skill 產生的 findings 檔，輸出的 findings 也保留它的報告產生器需要的欄位。

### 比對畫出來的東西而不是元素樹

規格列出範圍內所有元素，但只有「會畫出東西」的才是比對單位（以下稱可見元素）：有填色、漸層、框線、陰影或偽元素裝飾的方塊，文字區塊，圖示，圖片，輸入框。不畫任何東西的包裝層只保留盒模型數值，用來解釋距離。

理由：Figma 的圖層結構與 DOM 的元素結構幾乎不會相同，逐節點比對必須靠人工對齊名稱，這正是現行流程取樣不全與配對失敗的來源。畫面上有什麼則必須相同。

替代方案：維持以 id 與名稱配對的節點規格並擴充欄位。未採用，因為取樣上限與人工轉錄的問題不會消失。

### 以文字為錨點配對可見元素

配對順序：明確對應（呼叫者提供的對照表、元素上帶有的 Figma node id、共同的 test id）→ 文字內容相同的文字區塊（重複字串依閱讀順序）→ 圖稿相同的圖示與來源相同的圖片 → 包住相同文字集合的方塊（對方有沒有塗裝都算，以便把「缺少框線」這類差異指到可修改的元素上）→ 其餘元素依「在最小已配對外框內的相對位置與尺寸」→ 最後才是位置相符但沒有塗裝的元素。配不到的元素列為「沒有對應」，交由疊圖檢查判定。

實作期間補上的規則：以文字配對一律先於以位置配對（否則沒有塗裝的列會被旁邊的分隔線搶走對應）；厚度 4px 以內的細線不會以位置和厚度超過四倍的方塊配對；只有幾何的參考（唯讀 Figma）無法分辨圖片與矩形，文字以外的圖層可與文字以外的任何元素配對，而塗裝未知的 frame 排在所有其他圖層之後、以最接近者優先且只接受接近的對應。

理由：文字是兩邊最穩定的共同點；以外框內的相對位置配對，可避免上方一處位移讓下方全部配錯。

替代方案：以整頁座標的重疊面積配對。未採用，因為一處位移就會讓小元素（1px 分隔線）全部錯過。

### 位置以紅線距離量測

每個可見元素的四邊各量一條紅線：到同一外框內最近的相鄰元素，或到外框邊緣。要量哪一對邊由參考決定，兩邊量同一對。差異只在下列情況回報：參考那一側的距離是「設計出來的」（等於來源宣告的 padding、框線、margin、gap 的總和），或元素相對於兩側都移動了且不是維持置中。純粹是剩餘空間跟著別處變動的距離不回報。

宣告的版面數值不直接比對，只在距離不同時用來說明：設計由哪些數值組成、實作由哪些數值組成、哪一項不同。

理由：整頁座標的差異會連鎖（上方多 3px，下方全部被標記）；逐欄位比對 padding 與 gap 則會把畫面相同的不同寫法當成偏差，也看不到包裝層造成的位移。紅線距離同時避開兩者，而且就是設計師驗收時量的東西。

替代方案：比對每個元素相對於根節點的座標。保留為「位置通過率」這個分數與一致性判定的依據，但不作為修復清單。

### 結果分為原因與連帶結果

每個差異標記為原因或連帶結果。連帶結果是會隨原因修正而消失的差異：文字區塊因字級、行高、字距、內容不同而改變的尺寸；沒有明確尺寸的方塊因內容、外框或相鄰元素改變而改變的尺寸；參考中屬於剩餘空間、且旁邊有元素改變尺寸的距離；因文字對齊方式不同而產生的水平位移。方塊在來源中有明確寫出的寬或高時，其尺寸差異視為原因。若所有線索都被歸為連帶結果，變動最大的那一項提升為原因並註明無法解釋。

實作期間以基準測試逐項檢查「一個缺陷是否只回報一個原因」後，補上下列連帶結果：隨字級等比例變動的行高與字距（以 em 或倍數宣告）；兩邊宣告的間距總和相同、量到的距離卻不同，且旁邊有元素改變尺寸（間距本身沒錯，是量測對象變了）；差異只來自某元素的框線，而該框線本身已是一項發現；參考中屬於剩餘空間、實作的組成裡含有另一項發現已指出的錯誤數值；兩邊以相同位移釘住的定位元素。反過來，兩邊宣告了不同的最小或最大尺寸時，尺寸差異是原因，並在發現中寫出該限制。應截斷卻折行的文字只回報一項。

同一個差異出現在重複元件的多個實例，或同一個 padding 被多個子元素看到，合併為一項並列出實例數。

理由：實測中一個 padding 錯誤在現行流程會產生 6 到 54 個發現。AI 逐一修補症狀是修不到一致的主要原因之一。

### 相同畫面的不同畫法視為相同

圓角以實際生效值比較，兩邊都已全圓即視為相同；顏色一律轉為 sRGB 位元組後比較，每個色版容許 2；漸層與陰影解析後以標準形式比較；零位移零模糊的陰影視為框線（內側）或外環（外側），與 border、outline 合併比較，對應 Figma 的描邊位置；透明度以祖先連乘後的實際值比較；文字以套用大小寫轉換後的結果比較。

實作期間追加的等價寫法：分隔線畫成獨立的細長元素或畫成相鄰列的框線（細線貼齊並跨滿該邊時，視為該邊的框線，仍比對粗細與顏色）；漸層的各種寫法（方向關鍵字、角落關鍵字換算成該方塊的角度、省略位置的色標平均分布）；多層陰影的排列順序；`auto` margin 一律視為剩餘空間而不是宣告的距離。

理由：基準測試的陷阱都是實務上常見的等價寫法；回報它們會讓 AI 去改沒有問題的程式碼。

### 疊圖檢查是最後一道

兩張截圖在相同密度下逐像素比較（感知色差，與 pixelmatch 相同的量度），差異像素聚成區域，每個區域標出所在的可見元素，並輸出放大的「參考｜實作｜差異」對照圖。判定時允許一個像素的邊緣混色差異：某像素在另一張圖的 3×3 鄰域色彩範圍內即不計。同一種算圖引擎的色差門檻為 0.02，不同引擎（設計工具匯出圖對瀏覽器）為 0.05。

每個區域再標記為「已有解釋」（落在比對已回報差異的元素、位置不符的元素，或該元素在參考中原本的位置）或「沒有解釋」。沒有解釋的區域是屬性量不到的差異，必須逐一查看對照圖。外觀差異也會標記在這次截圖中是否看得見。

只落在「不必修」差異（adaptation、已套用的無障礙 remap）上的區域標記為已核可：會列出並計數，但不妨礙一致性判定——否則一個正確套用的 remap 會讓畫面永遠無法判定為一致。排除區域（`--ignore`）同時套用到三道檢查：區域內的像素不比對，中心落在區域內的可見元素也不配對、不比對、不計數，並在輸出中註明排除了幾個區域。

理由：屬性比對只能比規格能表達的東西。實測中原型未調整前漏掉的 5 個差異全部被疊圖檢查標出；反過來，疊圖看不到的差異（hover 狀態、被背景蓋住的透明度、0.25px 的線條粗細）由屬性比對負責。兩者互補，缺一不可。

替代方案：完全精確的像素比對。未採用，因為同一個全圓角用 border 或用內陰影畫，邊緣會有肉眼看不出的抗鋸齒差異，會讓相同的畫面無法通過。

### 以軟體算圖取得可重現的截圖

擷取用的瀏覽器固定以 sRGB 色彩設定與停用 GPU 算圖啟動；凍結動畫與轉場；等待字型載入；截圖前先丟棄一張，並重複擷取到連續兩張相同為止，無法穩定時回報。

理由：實測中 GPU 算圖下，同一頁面重新載入 14 次會得到 2 種不同的畫面（圓角與細線的抗鋸齒不同），載入後的第一張截圖也與之後的不同；停用 GPU 後 14 次完全相同。不可重現的截圖會讓相同的頁面被判定為不一致。

### 文字以行框量測並記錄實際使用的字型

文字區塊的位置與尺寸以重建的行框表示（行數乘以行高，寬度為文字實際範圍），與設計工具的文字框語意一致；行高未設定時量出瀏覽器的預設值並標記為未設定；記錄行數與是否被截斷。字型以瀏覽器實際用來繪製的字型為準，與要求的字型不符時標記字體環境不符；通用字型關鍵字（如 system-ui）不視為不符。

元素自己截掉的行（line clamp、固定高度加上隱藏溢出）不計入行數與範圍，並標記為被截斷。表單控制項裡顯示的文字（輸入值、選取的選項，或空白時的 placeholder）也記錄為文字元素；頁面無法量測控制項內部，所以它的位置以計算取得（內容區起點、單行垂直置中、以該字型量出的寬度）。這讓「輸入框內的文字離邊緣太近」能以 padding 差異回報，也讓 Figma 輸入框裡的文字圖層有對應。

理由：行內元素回報的高度是字型本身的高度而非行高，直接使用會讓每段文字都出現假的高度差異。

### 實作的擷取條件跟隨參考

量測循環擷取實作時，視窗寬度、密度、深淺色主題與要量測的互動狀態都取自參考：密度由參考截圖的寬度除以畫面寬度得出（沒有截圖時用參考規格記錄的密度），主題用參考規格記錄的值；都可用參數覆寫。擷取時由腳本指定頁面看到的 `prefers-color-scheme`，不沿用執行機器的設定。頁面載入失敗（找不到檔案、連線被拒、伺服器回應 400 以上）時以結束碼 2 結束，不會把瀏覽器的錯誤頁當成畫面擷取。

理由：實測中參考以密度 1 擷取、實作以預設密度 2 擷取時，相同的頁面會出現 32 個假的差異區域；主題跟著機器設定時，同一份參考在不同機器上會得到不同結果。

### 互動狀態以強制狀態擷取並比對內容

擷取時對每個互動元素逐一強制套用指定的狀態（hover、focus-visible 等），記錄相對於預設狀態改變的塗裝屬性；比對時逐項比較，不只檢查狀態是否存在。

### 同引擎同尺寸時行高與字距必須一致

參考與實作屬於同一類排版引擎（Figma 與 web 同屬 CSS 類）且尺寸相同時，行高與字距的差異列為 drift。跨引擎時維持 adaptation。幾何容差為 0.5px（文字寬度為 1px 或 1.5%，取較大者），宣告數值容差為 0.25。

理由：行高直接決定每一段文字的高度與整頁的垂直節奏，Figma 的行高與字距可以原樣在 CSS 重現。現行分類讓這類差異永遠不會被修。

### 既有分類規則移入新的比對腳本

下列行為由新的比對腳本承接，判定方式不變：無障礙 remap 的雙向判定、觸控目標最小尺寸、作業系統介面的忽略名單、觸控與指標裝置的狀態差異、字體環境不符時文字度量降為不可信、跨尺寸時間距與尺寸改為 adaptation 且不套用位置與疊圖判定、`platformOnly` 節點、估計值規格不回報 2px 以下的差異、以 policy 檔覆寫。發現的欄位保留 `severity`、`parityClass`、`ownership`、`recommendedFix`、`status` 等既有名稱。

沒有位置資訊的舊格式規格仍可輸入：以 id、名稱與文字配對，只比對外觀，判定標示為部分檢查，不會判為一致。

### Figma 端以唯讀 Plugin API 腳本擷取

提供一支只讀取、不修改檔案的 Plugin API 腳本，由可執行腳本的 Figma 工具執行，輸出與 web 端相同格式的節點：位置、auto layout 數值、填色、描邊（含位置與各邊粗細）、圓角、效果、文字屬性（含文字框是否固定寬高與對齊錨點）、元件名稱、綁定的 variable 名稱、是否固定尺寸。回傳以位移與筆數分頁，每頁不超過 18,000 字元；另一支本機腳本把各頁合併成完整規格並檢查沒有缺頁或重複。漸層與陰影優先採用 Figma 自己的 CSS 輸出，再以與 web 端相同的標準化處理。

理由：目前 Figma 端靠 AI 從產生的程式碼把數值抄進 JSON，是取樣與抄錯的來源。

替代方案：以 REST API 讀取。未採用為預設，因為需要另外的存取權杖。

### 只有唯讀 Figma MCP 時退回幾何規格

沒有可執行腳本的工具時，把 metadata 的節點樹（名稱、類型、位置、尺寸）轉成只有幾何的規格，紅線比對與疊圖檢查照常進行；外觀只針對有差異的元素，由 AI 從 design context 與 variable 定義補上。判定會標明外觀只檢查了一部分。

### 一致性判定與結束碼

量測循環的指令在下列條件全部成立時判定為一致並以 0 結束：沒有要修的原因、參考的可見元素全部配對、每個配對的元素都在參考的位置上、疊圖除了已核可的區域之外沒有差異區域且兩張圖尺寸相同。否則以 1 結束。用法錯誤、找不到瀏覽器或根節點、頁面無法載入時以 2 結束。沒有參考截圖時只判定外觀與位置，並在輸出中標明。

### 修復迴圈依進度停止

每一輪只修「要修的原因」，依 token、共用元件、組版、頁面的順序；不修連帶結果；沒有解釋的區域逐一查看對照圖後處理。每輪修完重新量測。要修的項目與沒有解釋的區域數量不再下降時停止並回報阻礙；分數下降或出現前一輪沒有的差異時視為修壞了，先還原該修改。上限為 8 輪；量測循環會透過前一輪的結果計算輪數，超過上限時印出警告。結束時每個剩餘項目都要有裁決：adaptation、已核可的 remap、或附理由的擱置。

理由：固定三輪的上限會在還有進展時停下。

### skill 名稱以資料夾名稱為準

使用者於 2026-10-02 決定統一名稱。方向是讓 frontmatter 跟著資料夾：主文件 frontmatter 的 name 改為 `ui-visual-parity`，標題改為 UI Visual Parity；description 與內文不變。repo 內以舊名稱 `ui-compare-to-reference` 稱呼本 skill 的地方共三處（`ds-to-storybook` 主文件兩處、`frontend-product-implementation` 的驗證說明一處），一併改為新名稱；這兩份文件的其他內容不動，包含它們對 `ui-pixel-align-report` 的引用。

理由：README、使用說明頁、workspace starter 的同步清單、wrapper 與指令，以及由範本建立的 workspace，全部以 `ui-visual-parity` 稱呼它；repo 內 10 個 skill 有 8 個的 name 與資料夾相同；skill 的慣例也要求 name 與所在資料夾同名，不一致時有些工具會忽略或警告。

替代方案：把資料夾改名為 `ui-compare-to-reference`（與另一個 skills repo 相同）。未採用，因為要改動 README、使用說明頁、workspace starter 與範本共 24 個檔案、60 多處引用，而且 workspace 是以資料夾路徑從上游同步，既有的 workspace 會同步不到。

影響：以舊名稱呼叫本 skill 的地方要改用新名稱。另一個 skills repo 的資料夾仍叫 `ui-compare-to-reference`；之後若把升級後的 skill 同步過去，那邊要保留原本的 name，或一併改名（範圍外，同步時處理）。

### 零相依的瀏覽器驅動與影像處理

以 Node 內建的 WebSocket 直接使用 Chrome DevTools Protocol，PNG 的讀寫以內建的 zlib 完成，不需安裝任何套件。擷取函式是單一檔案，也可由環境中已有的瀏覽器工具（Playwright、瀏覽器 MCP）直接執行。

理由：skill 會被複製到沒有套件安裝步驟的環境。

### 基準測試隨 skill 附上

兩個測試頁與差異清單放在 skill 的 tests 資料夾，每個差異宣告預期被指出的原因。執行後逐項檢查：對照組判定一致、每個差異都有符合預期的原因、每個陷阱都判定一致；任何一項不符即以非零結束。

## Implementation Contract

**行為**

- 在 skill 資料夾執行量測循環指令後，輸出資料夾會有實作規格、實作截圖、判定結果、疊圖與各區域的放大對照圖；終端輸出依序為判定、三個分數、要修的原因（含設計與實作的組成或 token）、連帶結果、沒有解釋的區域。
- 相同頁面（即使元素結構不同）判定為一致。

**介面**

- 量測循環：`parity.mjs`，參數 `--reference`（參考規格）、`--reference-image`、`--url`、`--root`、`--out`、`--previous`、`--viewport`、`--dpr`、`--theme`、`--states`、`--renderer`（same 或 other）、`--reference-density`、`--tolerance`、`--threshold`、`--ignore`、`--policy`、`--map`、`--remaps`、`--limit`。`--viewport`、`--dpr`、`--theme`、`--states` 未指定時取自參考。
- 擷取：`capture_web.mjs`，參數 `--url`、`--out`、`--name`、`--root`、`--viewport`、`--dpr`、`--theme`、`--states`；輸出規格與截圖。`extract_dom.js` 是可在頁面中求值的單一函式，接受 `root` 與 `name`。
- Figma：`extract_figma.js` 開頭的三個常數為節點 id、位移、筆數，回傳 `surface`、`total`、`offset`、`nextOffset`、`nodes`；`figma_to_spec.mjs` 以 `--parts` 合併分頁，或以 `--metadata` 產生幾何規格。
- 比對：`parity_diff.mjs`，參數 `--reference`、`--implementation`、`--output`、`--policy`、`--map`、`--remaps`、`--ignore`。
- 疊圖：`pixel_diff.mjs`，參數 `--reference`、`--implementation`、`--out`、`--spec`、`--reference-density`、`--implementation-density`、`--tolerance`、`--threshold`、`--ignore`。
- 規格 1.1 版的節點欄位：`id`、`parent`、`kind`（box、text、icon、image、input）、`paints`、`rect`（相對於根節點）、`layout`、`box`（padding、margin、borderWidth、fixed）、`background`、`gradient`、`border`、`radius`、`shadow`、`outline`、`opacity`、`opacityEffective`、`filter`、`backdropFilter`、`pseudo`、`type`（含 lineHeightSet、lines、truncated、align、transform、decoration）、`text`、`role`（控制項文字為 value 或 placeholder）、`fill`、`icon`、`image`、`placeholder`、`shows`、`states`、`tokenRefs`、`keys`、`selector`；`layout` 含定位元素被釘住的邊（pinned）與各邊位移（inset），`box` 含哪些 margin 是 auto（marginAuto）。`surface` 記錄平台、視窗、密度、主題、根節點、字型（要求的與實際繪製的）、保真度。
- 判定結果的欄位：`verdict`（parity、checked）、`scores`（primitives、appearance、geometry、toFix、consequences、leaveAlone、untrusted）、`parity`（含被 policy 排除的節點名稱 skipped 與排除區域數 ignoredAreas）、`findings`（id、gate、specField、intent、parityClass、severity、action、block、expected、actual、delta、derived、differs、designedAs、builtFrom、tokens、instances、visible、selector、ownership、recommendedFix、status）、`regions`（位置、像素數、owner、explained、sanctioned、crop）、`pixels`（含 unexplained 與 sanctioned 的數量）、`cycle`（第幾輪）。

**失敗情況**

- 找不到 Chromium 系列瀏覽器：說明如何以環境變數指定執行檔，結束碼 2。
- 根節點選擇器沒有符合的元素：結束碼 2。
- 頁面無法載入（找不到檔案、連線失敗、伺服器回應 400 以上）：說明原因，結束碼 2，不寫出任何檔案。
- 要求了瀏覽器無法維持的互動狀態，或 light、dark 以外的主題：列出可用的值，結束碼 2。
- 要求的具名字型沒有被用來繪製：照常輸出，加上字體環境不符的警告，文字度量的差異標為不可信。
- 截圖無法穩定：照常輸出並警告畫面仍在變動。
- 兩張截圖尺寸不同：比較重疊範圍，回報尺寸不符，不判定為一致。
- Figma 分頁有缺頁或重複：合併腳本以錯誤結束並指出缺少的範圍。
- 跨來源而無法讀取的樣式表：略過，token 的提示可能不完整，不影響比對。

**名稱**

- 主文件 frontmatter 的 name 等於資料夾名稱 `ui-visual-parity`。repo 內除了本 change 資料夾的歷史紀錄之外，不再出現 `ui-compare-to-reference`。

**驗收**

## Risks / Trade-offs

- [Figma 端腳本尚未在真實檔案上驗證（文字框語意、描邊位置、`getCSSAsync` 在腳本工具中是否可用、20kB 分頁）] → 列為獨立任務並需要使用者提供 frame；驗證前 skill 文件標明該路徑未驗證，並保留唯讀 MCP 的退回做法。
- [疊圖在 Figma 匯出圖對瀏覽器截圖時的雜訊，只以替代條件校正過（整頁位移 0.4px、切換文字抗鋸齒）] → 門檻與容差可由參數調整；真實檔案驗證時一併校正並把結果寫回文件。
- [原因與連帶結果的判斷是啟發式，可能排錯順序] → 連帶結果仍會列出；每輪修完重新量測；全部被歸為連帶結果時自動提升一項；疊圖檢查不受這個判斷影響。
- [基準測試曾用來調整原型，數字偏樂觀] → 在 Context 記錄了調整前的數字（設定頁 26 個）；真實專案上預期會再遇到新的缺口，由疊圖檢查接住並回饋為新的測試案例。
- [擷取只涵蓋主文件的 DOM：shadow DOM、iframe、canvas 內容不會展開] → 這些區域由疊圖檢查涵蓋；在量測說明中列出。
- [偽元素沒有可量測的位置，只比對外觀、尺寸與定位值] → 位置差異由疊圖檢查涵蓋。
- [停用 GPU 的算圖與使用者實際瀏覽器的字體抗鋸齒不同] → 兩邊在同一條件下擷取時不影響比較；對 Figma 匯出圖則屬於已容許的跨引擎差異。
- [樣式表掃描以「後面的規則優先」近似層疊順序] → 只用於提示 token。明確尺寸、釘住的邊與 auto margin 改由瀏覽器回報的層疊結果（版面計算前的值）取得；瀏覽器不提供時才退回樣式表掃描，此時判斷錯誤影響的是原因與連帶結果的排序，不影響是否被發現。
- [控制項內文字的位置是計算值而非量測值] → 兩邊都是 web 時以同一方法計算，相同即相同；原生外觀的下拉選單內距不在計算內，對 Figma 比對時可能有數 px 的誤差，由疊圖檢查佐證。
- [分隔線與框線的等價判定以「貼齊且跨滿該邊」為條件] → 內縮的分隔線不會被視為框線，仍以缺少與多出回報。
- [容差收緊後，舊專案可能出現大量 1px 差異] → 以 policy 檔可調回；回報時合併重複實例。
- [需要 Node 22 以上與本機瀏覽器] → 環境已有瀏覽器工具時可直接執行擷取函式；兩者都沒有時退回既有的精簡比對並標示為估計值。
