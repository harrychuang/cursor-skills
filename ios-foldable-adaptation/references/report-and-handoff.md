# 報告、Before／After 與設計師交接

設計師靠報告上的前後對照審閱結果，所以「改了版面」這件事沒有附截圖就等於沒做完。這份定義每一輪要交什麼、怎麼命名、什麼東西要回去問設計師。

## 1. 每一輪的交付

| 產物 | 內容 | 工具 |
|---|---|---|
| QC 報告（HTML） | 摘要數字、怎麼測的、本次修改、HIG 對照、問題清單（規則＋人工）、每頁各姿態截圖（可放大、編號彈窗）、已知限制、下一步 | `scripts/report.py` + `context.json` + `commentary.json` |
| 版面調整 Before／After | 每項修改：修改前、修改後截圖各一組，一句話說明；放在報告最前面，最新一輪在最前 | 用 `context.repros` 或直接在 HTML 加區塊（莎拉的做法） |
| 決策紀錄 | 問卷答案、決定者、日期、改過的決定 | `templates/duo-decisions.md` |
| 待決清單 | 要設計師回答的問題，每條附截圖與影響範圍 | 報告的「限制與注意」＋對話 |
| 驗證結果 | 單元測試數、整合測試幾／幾、走訪幾張、人工看過幾張 | `context.changes.verification` |
| 給人看的說明文件（選用） | 設計方向、每個決策一組前後對照、取捨；Apple 風格 HTML 與 Figma 畫板 | 莎拉的 `scripts/duo-qc/design-doc/`（`template.html` + `build.py`）可當範本 |

## 2. Before／After 的規則

1. **改之前先確認手上有同一頁、同一姿態的舊截圖**。沒有就先跑一次 QC 留底，再改。
2. **「修改後」一律是目前版本**：某次修改會改變其他項目截圖裡看得到的東西（共用的直欄、按鈕、底色）時，發布前重跑全頁走訪，把所有項目的「修改後」換成最新截圖；不要用文字註記代替重拍。設計師會把報告上每一張「修改後」當成現況檢查，不會看輪次標籤。
3. **「修改前」維持該項修改之前的畫面**，標上輪次或日期。
4. 一項修改一個區塊：標題（頁面・姿態・做了什麼）、一句為什麼、尺寸、前後各一到三張。第五輪起莎拉的報告把每一輪的新項目放最前面。
5. 截圖來源統一用主機截圖（`shots/`）或套用螢幕外形的版本（`shots-masked/`，看圓角時用）；同一個區塊不要混用。
6. 沒有改變的姿態也放一張，標「未變動」，證明沒有回歸（例如內螢幕直向）。

## 3. 報告的 context.json 怎麼寫

範例在 `assets/report-context.example.json`。要點：

- `title`／`subtitle`／`meta`（日期、裝置、分支、變更提案）。
- `runs`：每個情境的標籤與一句說明，順序就是報告順序。
- `changes`：本次修改清單（可連到 Before／After 的 anchor）、驗證表（項目／結果／說明）、取捨。
- `hig`：逐條對照（`references/hig-summary.md` 的 H1～V10），狀態符合／部分／不符合／待確認＋證據。
- `hide_rules`／`rule_ids`／`extra_removed`／`removed_note`：與團隊確認不處理的編號保留、不列出，其餘編號不變（設計師靠編號溝通）。
- `limits`：已知限制與待確認，每條寫清楚「是系統限制」還是「等決定」。
- `next`：建議下一步。

人工看到的問題寫進 `commentary.json`（`id` 固定、`box` 畫框、`status: "fixed"` 表示已修、`hidden: true` 表示已確認不是問題）。

## 4. 什麼要回去問設計師（不要自己決定）

- 問卷（`references/questionnaire.md`）任何一題的答案改變。
- 版面規則裡標「暫定值」的數字（左欄 360 pt、側欄 120 pt、頁籤列最低高度 36）。
- 會連一般 iPhone 一起改變的事（header 裡的分組、返回鍵樣式）。
- 外部套件做不到的事（橫排頁籤、清單選中反白、自動播放計次）：列出要不要請套件維護者改。
- 系統限制造成的取捨（只開一個橫向、有 Tab 的頁面按鈕排不到底部、寬膠囊留在 header）。
- 任何「做完後覺得怪」但規則沒講到的畫面：截圖＋一句描述，問就好。

問的時候附：截圖、影響哪些頁、兩個以上的選項與各自代價、建議。設計師回覆後更新決策紀錄，再改。

## 5. 輪次節奏（莎拉六輪的實際流程）

1. 跑 QC → 報告 → 設計審閱提出修改（通常 2～4 項）。
2. 工程在實驗 app 量 iOS 行為（不確定系統允不允許時先做小實驗，不要直接在產品上試）。
3. 寫變更提案／設計（Spectra 或等價文件）、實作在預設關閉的開關後面、補單元與整合測試。
4. 重跑受影響的情境（姿態切換、整合測試）＋全頁走訪，逐張看。
5. 報告：新一輪的 Before／After 放最前面、舊項目的「修改後」重拍、驗證表、限制與待決。
6. 設計審閱 → 下一輪。每輪約一天。

## 6. 發布

- 報告發布成私人網頁（claude.ai Artifact 或等價）時把 `--full-dir` 的 `img/` 一起上傳，點截圖可看大圖；同一份報告沿用同一個網址、改版號。
- 說明文件若要給公司外的人看，先遮掉測試帳號的 email 等個資。
